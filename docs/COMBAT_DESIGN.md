# 전투 시뮬레이션 설계: 고정 타임스텝 + 보간 + CCD

상태: **구현과 검증 완료(2026-11-23), 5절 결정은 모두 추천안으로 승인.** 검증 결과는 6절, 구현 중 드러난 한계는 3-7과 7절.

## 1. 문제

### 1-1. 몬스터가 플레이어 몸을 통과한다 (경로 두 개)

- **긴 프레임(터널링).** 몬스터는 `RunSpeed × Time.deltaTime`만큼 순간이동한다. Unity가 한 프레임을 최대 0.333초로 자르므로 한 번에 최대 3.4 × 0.333 = 1.133을 움직이고, 이동 도중에는 아무 판정도 하지 않는다. 플레이어가 몬스터를 잡는 구간은 "플레이어 중심 앞 ~ 교전 거리"인데 슬라임은 0.9, BossUndead는 0.6이라 한 번에 건너뛴다.
- **달리는 중 수동 스킬(프레임과 무관).** 스킬 슬롯을 탭하면 `PlayerRunState` → `PlayerSkillState`로 바로 가는데, 스크롤(`IsScrolling`)은 공격 상태에 들어갈 때만 꺼진다. 그래서 시전하는 동안(스킬 클립 1.0초, 힐 0.6초) 배경과 몬스터는 계속 움직이고 사거리 판정은 없다. 대상이 약 4.2 안쪽에 있으면 몸을 통과한다. 대상은 스킬이 끝난 뒤 공격 상태가 위치와 상관없이 계속 때리므로 정지까지는 안 가지만, 뒤에 있는 몬스터를 앞을 보고 때리는 모습이 된다.

### 1-2. 통과하면 영구 정지가 되는 이유

플레이어는 앞쪽 몬스터만 찾는다(`MonsterSpawner.GetClosestMonster`의 `distance > 0`). 반면 인카운터 종료(`AllDie`), 범위 스킬(`GetMonstersInRange`), 보스 판정은 앞뒤를 다 본다. 뒤로 넘어간 몬스터는 공격받지 않는데 살아 있는 것으로 세어져서 다음 스폰이 영원히 오지 않는다. BossUndead는 뒤에서 플레이어를 공격하고, 플레이어는 반격하지 못하고 죽어 스테이지 재시작이 반복된다.

### 1-3. 프레임에 따라 결과가 달라지는 것

- 공격 타이머가 `timer = 0f`로 넘친 시간을 버려서, 실제 공격 간격이 프레임 길이만큼 늘어난다(30fps와 120fps의 초당 데미지가 다름).
- 교전을 시작하는 위치가 프레임마다 다르다.
- 타격 시점은 애니메이션 이벤트가 정하는데, 애니메이터는 화면 프레임 기준(Update Mode: Normal)으로 돈다.
- 스폰 루프는 `yield return null`과 `WaitForSeconds`라서 화면 프레임 단위로 진행된다.

## 2. 목표와 보장

| | 보장 | 수단 |
|---|---|---|
| G1 | 살아 있는 몬스터는 플레이어 몸을 통과하지 않는다. 단계 크기와 플레이어 상태에 상관없이. | CCD(3-4) + 스크롤 소유 정리(3-5) |
| G2 | 한 스테이지 안의 전투 결과(처치 시각, 골드)가 화면 프레임률과 무관하다. 30fps든 120fps든 렉이 섞이든 같다. | 고정 타임스텝(3-1, 3-2) + 애니메이터(3-6) + 타이머(3-7) |
| G3 | 120Hz 화면에서도 몬스터와 배경이 매끄럽게 움직인다. | 보간(3-3) |

G1과 G2는 서로 독립이다. CCD만으로도 정지 버그는 막히고, 고정 타임스텝은 "결과가 프레임에 따라 달라지는" 문제 전체를 위한 것이다.

**보장하지 않는 것**
- **심한 렉에서 실제 시간과 맞추기.** 한 프레임 상한(Maximum Allowed Timestep 0.333초)을 그대로 둔다. 1초 동안 멈추면 게임 시간은 0.333초만 흐른다. 상한을 올리면 저사양 기기에서 따라잡는 계산 때문에 더 느려지는 악순환이 생긴다. 앱이 꺼져 있던 긴 시간은 시뮬레이션이 아니라 오프라인 보상으로 다룬다.
- **스테이지 전환을 넘는 재현.** 전환 페이드(`FadeController`)는 연출이라 화면 시간으로 돈다. 그래서 전환 직후 시뮬레이션이 다시 시작하는 시점이 최대 한 화면 프레임 다를 수 있다.
- **기기 사이 비트 단위 일치.** PC 에디터와 Android(ARM64)는 부동소수점 결과가 미세하게 다를 수 있다.

## 3. 구조

### 3-1. `CombatSimulation`: 전투의 유일한 고정 단계

씬에 하나 있는 MonoBehaviour다. 전투에서 `FixedUpdate`를 쓰는 곳은 여기뿐이고, 한 단계(0.02초)마다 정해진 순서로 진행한다.

```
FixedUpdate (0.02초마다)
  1. 몬스터 위치를 시뮬레이션 위치로 되돌린다 (보간이 그려 둔 위치를 지움)
  2. 플레이어 Tick: 미뤄 둔 입력 적용 → FSM → 스킬 쿨다운
  3. 몬스터 Tick (스포너 목록 순서): FSM(이동 + CCD) → 보스 스킬 쿨다운
  4. 배경 Tick
  5. 몬스터와 배경의 이번 단계 상태를 기록한다 (보간용 이전/현재)
  -- 이어서 Unity가 같은 단계 안에서 진행 --
  6. 애니메이터(Fixed 모드) 갱신 → 애니메이션 이벤트(타격, 동작 끝)
  7. WaitForFixedUpdate로 기다리던 코루틴 재개 (스폰 루프)

Update (화면 프레임마다)
  alpha = (Time.time − Time.fixedTime) / Time.fixedDeltaTime
  몬스터와 배경을 이전/현재 상태 사이 alpha 지점에 그린다
```

- **조립:** `GameInitializer`가 `GameManager.Initialize` 다음에 `combatSimulation.Initialize(player)`를 부른다. 스포너와 배경은 씬 참조(SerializeField)다. 초기화 전에는 아무것도 돌지 않는다(지금 `PlayerController.Update`의 `stats == null` 검사와 같은 역할).
- `PlayerController`, `Monster`, `BossMonster`의 `Update`는 `Tick()`으로 바뀌고 이 클래스만 부른다. `BackgroundScroller.LateUpdate`도 `Tick()`과 보간 적용으로 나뉜다.
- **각 객체가 직접 `FixedUpdate`를 쓰지 않는 이유:** 1번(되돌리기)과 5번(기록)은 모든 전투 로직의 앞뒤에 와야 한다. 각자 `FixedUpdate`를 쓰면 이 순서를 실행 순서 속성과 코루틴 훅에 흩어서 맞춰야 한다. 한 곳에 두면 순서가 코드 한 화면에 드러난다. 업계에서 흔히 쓰는 "관리자가 Update를 대신 부르는" 패턴이다.

### 3-2. 시간 규칙

- **위치를 읽거나 움직이는 전투 로직과 전투 타이머는 고정 단계 안에서만 실행한다.** 그 안에서 `Time.deltaTime`은 Unity가 `Time.fixedDeltaTime`(0.02)을 돌려주므로, 상태 코드의 `Time.deltaTime`은 그대로 둔다.
- **UI 입력 중 위치를 읽는 것은 다음 단계로 미룬다.** 지금 해당하는 것은 스킬 슬롯 탭(대상 선택에 위치를 씀) 하나다. `TryUseSkillSlot` 대신 `RequestSkillSlot`이 요청을 저장하고, 다음 `Tick`의 맨 앞에서 처리한다. 지연은 최대 0.02초다.
- **위치를 읽지 않는 상태 변경은 단계 사이에 그대로 한다.** 업그레이드, 스킬 장착, 보스 도전 시작, 스테이지 전환이 해당한다. Unity는 고정 단계를 다 돌린 뒤에 UI 이벤트를 처리하므로, 단계 중간에 끼어들지 않는다.
- **스폰 루프는 고정 단계를 센다.** `GameManager`의 인카운터 반복과 보스전 대기는 `yield return null` 대신 `WaitForFixedUpdate`, `WaitForSeconds` 대신 단계 수로 기다린다. 스테이지 전환 페이드는 화면 시간 그대로 둔다(2절 "보장하지 않는 것").

### 3-3. 보간

- **대상은 움직이는 것뿐이다.** 몬스터의 위치와 배경 UV 오프셋이 해당한다. 플레이어는 제자리라 제외한다.
- **몬스터:** 이전/현재 위치 두 개를 갖는다. **스폰할 때(`Monster.Initialize`) 둘 다 새 위치로 맞춘다.** 그러지 않으면 풀에서 꺼낸 몬스터가 죽었던 자리에서 한 프레임 미끄러져 오는 게 보인다.
- **배경:** 오프셋 이전/현재 두 개를 갖는다. 1을 넘겨 감을 때는 둘에서 똑같이 1을 빼서, 보간이 0과 1 사이를 거꾸로 훑지 않게 한다.
- **비용:** 화면이 최대 한 단계(0.02초) 늦게 그려진다. 타격 이펙트와 데미지 숫자는 판정 위치에 생긴다. 맞는 몬스터는 대부분 멈춰 있고, 걸어오는 보스라도 그려진 위치와의 차이는 한 단계 이동량(0.068) 이하다.
- **채택하지 않은 대안: Kinematic `Rigidbody2D` + Interpolate.** Unity 내장 보간이지만 배경은 어차피 직접 보간해야 한다. 또 지금 없는 물리 구성 요소를 캐릭터에 들이면 트리거 콜라이더 동작이 바뀌는 등 부작용이 생긴다.

### 3-4. CCD: 몬스터는 플레이어 몸을 통과하지 않는다

- **규칙:** 살아 있는 몬스터는 접촉선보다 안쪽으로 이동하지 않는다. 접촉선은 `플레이어 x + 플레이어 반너비 + 몬스터 반너비`, 즉 두 몸이 닿는 위치다.
- **위치:** `Monster.moveToPlayer` 한 곳이다. 일반 몬스터와 보스가 같이 쓴다.
  ```
  next = max(x − step, min(x, contactX))
  ```
  - 접촉선 앞에 있으면 접촉선에서 멈춘다.
  - 이미 겹쳐 있으면(순간이동 등) 더 파고들지 않고 그 자리에 있는다.
- **접촉선에서는 교전이 반드시 시작된다.** 표면 사이 거리가 0이고 사거리는 0 이상이다. 그래서 늦어도 다음 단계에는 달리기 상태의 플레이어도, 자기 판정을 하는 보스도 공격으로 넘어간다.
- **앞서 제안한 "단계 크기 조건 검사"는 넣지 않는다.** CCD가 있으면 한 단계 이동량이 교전 거리보다 커져도 통과가 일어나지 않으므로, 지켜야 할 조건 자체가 없다. 지금 수치에서는 한 단계 이동(0.068)이 플레이어 사거리(0.1)보다 작아서, 정상 플레이 중에는 접촉선에 닿기 전에 교전이 시작된다. CCD는 개입하지 않는 안전망이다.
- **다루지 않는 것:** 위치를 직접 정하는 순간이동은 다루지 않는다. 지금 스폰 위치는 씬에 고정된 좌표(x 6.91부터 3.0 간격)라 해당 경로가 없다.

### 3-5. 스크롤의 주인은 달리기 상태

- **지금:** `IsScrolling`을 `PlayerRunState.Enter`가 켜고 `PlayerAttackState.Enter`가 끈다. 그래서 달리기에서 바로 스킬로 가면 켜진 채 남는다(1-1의 두 번째 경로). 시전 중에는 플레이어가 달리기 모션 없이 미끄러져 보인다.
- **변경:** `PlayerRunState.Enter`가 켜고 `PlayerRunState.Exit`가 끈다. "스크롤 = 플레이어가 달리는 중"이라는 규칙 하나로 정리하고, `PlayerAttackState.Enter`의 끄기는 지운다.
- **행동 변화:** 달리는 중에 수동 스킬을 쓰면 시전하는 동안 배경과 몬스터가 멈춘다.

### 3-6. 애니메이터

- 플레이어(`PlayerWarrior`)와 몬스터 4종(`BlueSlime`, `BlueSlime2`, `BossSlime`, `BossUndead`) 프리팹의 Animator Update Mode를 Normal에서 **Fixed**(예전 이름 Animate Physics)로 바꾼다. 타격(`AE_OnHit`)과 동작 끝(`AE_OnAttackEnd`)이 고정 단계에 맞춰 일어난다.
- 클립이 초당 10장짜리 스프라이트 애니메이션이라, 초당 50번 갱신해도 눈에 보이는 차이는 없다. 루트 모션은 모두 꺼져 있어 위치에 영향이 없다.
- 이펙트처럼 전투 판정과 무관한 Animator는 그대로 둔다.

### 3-7. 공격 타이머

- **지금:** `timer = 0f`. 고정 단계에서는 기기와 무관해지지만, 간격이 0.02초 단위로 올림된다. 공격 간격이 0.1초면 최대 20% 느려진다. 또 부동소수점 오차 때문에 딱 나누어떨어지는 간격도 한 단계 늦을 수 있다.
- **변경:** 이번 단계에 막 넘은 경우에만 넘친 조각(한 단계 미만)을 다음 간격으로 넘긴다. 애니메이션이 끝나기를 기다리느라 늦어진 시간은 넘기지 않는다. 넘기면 다음 공격이 앞당겨져 몰아치기가 생긴다.
  ```
  overflow = timer − interval
  timer = overflow < Time.fixedDeltaTime ? overflow : 0
  ```
- `PlayerAttackState`와 `BossAttackState`에 같이 적용한다(`AttackTimer.NextStart`).
- **구현 후 측정에서 드러난 한계:** 간격 1.0초에서는 실제 간격이 정확히 1.0초다. 하지만 간격 0.1초(공격속도 최대)에서는 **0.14초**다. 병목은 타이머가 아니라 애니메이터 왕복이다. 다음 공격은 Attack → (종료 시간) → Idle → (트리거) → Attack을 한 바퀴 돌고, 끝 이벤트로 `isAnimationFinished`가 풀린 뒤에야 시작된다. Unity는 한 단계 안에서 스크립트를 먼저, 애니메이션 이벤트를 나중에 처리하므로 이 왕복에 두 단계가 더 든다. 화면 프레임 기준이던 수정 전에도 같은 구조였다(추정: 120Hz 0.117초, 30Hz 0.167초). 이번 변경으로 모든 기기에서 0.14초로 같아졌다. 고치려면 공격 연출 구조를 바꿔야 해서 따로 결정한다(`TODO.md` "전투").

## 5. 결정할 것 (추천 포함)

1. **틱 소유:** `CombatSimulation` 한 곳 **(추천)** / 각 객체가 직접 `FixedUpdate` + 실행 순서 속성.
2. **단계 크기 조건 검사:** 넣지 않고 CCD만 **(추천, 3-4)** / 둘 다.
3. **스크롤 = 달리기 상태 (3-5):** 수동 스킬 시전 중 세상이 멈추는 쪽 **(추천)** / 지금처럼 계속 흐름(이 경우 CCD가 대상을 몸 앞에 세우고, 대상은 배경 위에서 미끄러져 보임).
4. **애니메이터 Fixed (3-6):** 바꿈 **(추천)** / Normal 유지(타격 시점만 화면 프레임 기준으로 남음).
5. **공격 타이머 이월 (3-7):** 적용 **(추천)** / `timer = 0f` 유지.
6. **재현 범위:** 스테이지 안 **(추천, 페이드는 화면 시간)** / 페이드까지 고정 단계.

## 7. 범위 밖 (`TODO.md`에 기록)

- **공격속도가 빠를 때 애니메이터 왕복 지연**(3-7). 공격 연출 구조를 바꿀지 결정이 필요하다.
- **Android 렌더 프레임률.** 코드에 `Application.targetFrameRate` 설정이 없어 Unity 모바일 기본값으로 그린다(30fps로 알고 있으나 기기에서 측정하지 않음). 그래서 S24의 120Hz 화면을 실제로 쓰지 않는다. 보간은 렌더 프레임률과 상관없이 동작한다. 올릴지는 배터리와의 선택이다.

- **스크롤이 "달리기 상태의 몬스터가 스스로 이동"으로 구현돼 있음.** 그래서 달리기 상태가 아닌 것은 배경과 따로 논다.
  - 시체는 플레이어가 다음 몬스터로 달려가는 동안 화면에 붙어 같이 미끄러진다(코드상).
  - 공격 중인 보스는 스크롤을 따라오지 않는다. 보스의 교전 거리가 플레이어보다 길면, 보스는 멈춰서 때리고 플레이어는 제자리 달리기만 하는 교착이 생긴다. 지금 `.asset` 데이터는 둘 다 사거리 0.1이라 교전 거리가 같아 생기지 않는다. 다만 `MonsterDatabase.json`에는 BossSlime 사거리가 1.0으로 남아 있어, 재동기화하면 생긴다.
  - 근본 해결은 월드 스크롤을 한 곳이 소유하고, 배경과 모든 월드 오브젝트를 같은 양만큼 옮기는 구조다. 이번 CCD는 그 구조에서도 "스크롤 양을 첫 접촉까지로 제한"으로 그대로 옮겨 갈 수 있다.
- **타겟 규칙의 비대칭**(앞쪽만 vs 앞뒤 모두). 이동 경로의 통과는 CCD가 막지만, 순간이동으로 뒤에 놓인 몬스터는 여전히 영구 정지를 만든다.
- **스테이지 전환 페이드가 화면 시간으로 돈다**(2절).
