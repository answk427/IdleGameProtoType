- **Unity 6000.4.9f1.** 목표 플랫폼은 **Android**라 최종 확인에는 Android Build Support 모듈(SDK/NDK/JDK)과 실기기 또는 에뮬레이터가 필요하다. WebGL Build Support는 데모 빌드를 요청받았을 때만 필요하다. `Library` 없이 받아도 그대로 열린다(새 clone에서 컴파일, 테스트, 씬 부팅 확인).
- **Android:** 회사 PC는 준비 완료(2026-11-23) — Android 모듈 설치, 패키지 이름 `com.answk427.idleproto`, 첫 개발 빌드가 실기기(S24 Ultra)에서 실행됨. adb 공유 규칙과 PC별 설정(`ADB`, `ANDROID_SERIAL`)은 CLAUDE.md "외부 도구". 집 PC는 아직 Android 모듈과 기기 설정이 안 돼 있다.

### 2. 작업 방식 (사용자와 합의)

- 한 항목씩 **제안 → 사용자 확인 → 실행.** 커밋과 push는 명시적으로 지시받을 때만. "정리해"는 분류해서 보고만 하고 스테이징도 하지 않는다.
- **UI는 UI_DESIGN이 기준.** 바꾸자고 하기 전에 11장을 읽고, 원안에 작은 구현 규칙을 더해서 되는지 먼저 시험한다.
- 구현 중 합의한 설계를 구조적으로 바꿔야 하면 멈추고 먼저 묻는다.
- 프로젝트 성격은 **포트폴리오 유지**, 단 세이브 유실 금지는 원칙.
- **검증용 세이브는 사용자 세이브와 분리한다.** 켜 둔 에디터(Pipeline)에서는 플레이 전에 `claude` 세이브 프로필을 켠다(CLAUDE.md "외부 도구"). 배치 모드는 기본 세이브가 이미 있으면 플레이 확인을 중단한다. 일회성 측정 스크립트는 저장소에 넣지 않는다.
- **테스트는 작성해도 된다(2026-11-23 변경).** 반복해서 쓸 검증은 `Assets/Tests/EditMode/`에 테스트로 둔다. 불변식과 극단값을 확인한다(CLAUDE.md "작업 시 주의사항").
- **목표 플랫폼은 Android (2026-11-23 결정).** 검증은 단계별로 나눈다.
  - 수정과 확인을 반복할 때: 실행 중인 에디터(Pipeline, 회사 PC에서 연결 확인)나 배치 모드. 배치 모드는 화면을 못 본다.
  - 플랫폼 동작과 최종 확인: **Android 빌드 + adb**(설치, 화면 캡처, logcat, 터치/뒤로가기 입력). 뒤로가기, 터치, 앱 내렸다 올릴 때 저장, SafeArea, 성능은 여기서만 확인된다.
  - **WebGL은 정식 검증 과정에서 뺀다.** 포트폴리오 데모 공개 계획은 있지만, WebGL 빌드와 확인은 사용자가 명확히 요청할 때만 한다. (이전 세션은 화면 확인용 대용품으로 WebGL을 썼다. 숨은 탭 3fps, IndexedDB 저장 등 Android와 다른 결과가 섞인다.)

### 3. 완료된 것

- **설계 확정:** UI_DESIGN, SERVER_DESIGN.
- **0단계:** `GameNumber`, `GameSession`, `GameInitializer`.
- **1차 수직 슬라이스:** 스킬 관리 창 하나가 `WindowRegistry` → `WindowManager` → `SkillManagePresenter` → 반응형 구독/자동 해제 → `InputBlocker`를 통과한다(`Assets/Scripts/UI/Core/`). 기존 `UIManager`(HUD, 탭)와의 연결은 `UIRoot` 한 곳. 새 팝업은 `UIWindow`로 만든다(절차는 CLAUDE.md "UI 구조").
- **손상 세이브 유실 수정:** `SaveDataValidator`. 남은 것은 아래 "저장".
- **전투 영구 정지 수정 (2026-11-23):** 고정 타임스텝(`CombatSimulation`) + 화면 보간 + CCD. 설계와 검증 결과는 [COMBAT_DESIGN.md](COMBAT_DESIGN.md). 재현법 시드 1~3이 1500초 동안 멈추지 않고, 30fps/120fps/렉 섞기의 처치 시각이 소수점까지 같다. 남은 것은 아래 "전투".
- **전투 1단계: 행동 시간표 (2026-11-24):** 전투 로직이 애니메이션 이벤트·전이를 읽지 않는다. 공격 간격이 설정 그대로(0.1초 설정이 0.14초가 되던 문제 해결), 보스 간격이 데이터대로, 스킬 쿨다운이 슬롯이 아니라 스킬 id 기준, 애니메이터를 꺼도 결과가 같다. 시간 처리는 시계 하나·절대 시각·전투원 전체의 시간 순서 사건 처리(`SimClock`, `CombatScheduler`)로 만들었다. 결과는 [COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 7-10, 7-12. 이어서 **취소 없음**(모든 행동은 끝까지, 다음 행동은 완료 뒤)과 **행동 길이는 데이터**(스킬 = `SkillData.castTime`, 애니메이션은 타격 비율만)로 규칙을 정했다(7-13). S24에서 실행·전투·에러 로그 0건 확인(움직임 눈 확인은 사용자).
- **전투 2단계: 전투원 통합 (2026-11-24):** 플레이어·일반 몬스터·보스가 `Combatant`(순수 C#) 하나이고, 차이는 데이터다(일반 몬스터의 공격도 엑셀만으로 켠다). 판정은 표면 거리 하나, 대상은 앞뒤 무관. HP·데미지 `GameNumber`, 전투 중 할당 0(테스트), 상태 객체 제거. 엑셀 캐릭터 시트(사거리, 이동 속도)와 몬스터 `movePolicy` 열을 더했고, 엑셀을 고치지 않고 값을 바꿔 보는 튜닝 덮어쓰기(`IdleGame/Data/Tuning Overrides`)와 데이터·프리팹 짝 검사를 만들었다. 일반 전투와 BossSlime의 처치·타격 시각이 1단계와 비트 단위로 같다. 결과는 [COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 8-11.
- **전투 3단계: 공간 모델 (2026-11-25):** 플레이어가 월드에서 실제로 전진하고 카메라가 따라간다. 시체·동전·이펙트는 아무 처리 없이 화면에서 지나간다. 이동은 sweep 하나(전진·접근 공통), 인카운터마다 원점 재설정(1시간 달려도 좌표 10 이하), 보스 이동 속도와 스폰 거리는 엑셀 데이터(`moveSpeed`, `spawnDistance`). 스크롤 개념을 지웠다. 결과는 [COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 9-7.
- **개발자 도구 (2026-11-25):** 에디터와 개발 빌드에만 있는 패널(스테이지 이동, 보스전, 골드·경험치, 레벨 지정, 백업·복원·새로 시작, 배속, 판정 몸 표시). 릴리스 빌드에는 어셈블리째 없다. 흐름 입구를 `GameManager.RestartAt` 하나로 합쳤고(사망·클리어·이동), 실행 중 진행도 교체(`LoadSnapshot`, 서버 롤백이 쓸 길)를 만들면서 교체 뒤 HUD·캐릭터 능력치가 옛 값으로 남던 빈틈(`OnReloaded`)을 고쳤다. 검증은 사용자 에디터를 닫지 않고 검증용 사본 프로젝트에서 했다(CLAUDE.md "외부 도구"). 결과는 [DEV_TOOLS.md](DEV_TOOLS.md) 7절.
- **전투 4-A: 흐름 (2026-11-25):** 인카운터·보스·스테이지 흐름이 `EncounterDirector`(순수 C#, 고정 단계 ①) 한 곳에 있다. `StageManager`, `GlobalGameEvents`, `GameManager`의 흐름 코루틴을 지웠다. 보스 버튼과 스테이지 안내는 View + Presenter로 흐름의 상태를 구독하고(버튼이 상태와 어긋나던 버그 해결), 스테이지 전환이 시뮬레이션 시간이라 프레임률과 무관하게 결정적이다(전에는 페이드가 화면 시간이라 전환 뒤가 갈렸다). 흐름 시간은 데이터(`BalanceConfig`), 보스전 제한 시간 열(`bossTimeLimit`, 지금 모두 0), 진전 감시 경고를 더했다. 측정 중 시뮬레이션 단계 길이가 0.0199999921이던 것을 찾아 0.02로 고쳤다. 결과는 [COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 10-9.
- **전투 4-B: 진행도 표시 (2026-11-26):** 진행도 모델(레벨, 경험치, 업그레이드, 골드)과 정적 버스가 반응형이다(상태·파생 상태·사건, `DerivedProperty<T>`). 과도기 장치 `OnReloaded`가 없어도 진행도 교체 뒤 화면과 캐릭터가 맞고, 레벨업이 바로 저장된다. HUD는 View + Presenter(보스전 남은 시간 포함, 엑셀 값만으로 켜진다), 데미지 숫자는 HUD·탭바 아래로 그려진다. `UIManager`에는 탭만 남았다. 테스트가 처음으로 모두 통과한다(196개, 실패하던 `AddExp` 2개를 지금 규칙으로 고쳐 씀). 결과는 [COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 10-11.
- **세이브 오류 창 (2026-11-26):** 세이브를 읽지 못하거나 저장된 스테이지가 데이터에 없으면 System 구분의 창(닫히지 않음, "게임 종료"만)이 "세이브 파일은 바꾸지 않았다"를 알리고, 딤이 탭바를 막는다(전에는 콘솔 에러뿐이었고 탭이 눌려 예외가 났다). 이를 위해 `UIRoot` 준비를 `Prepare`/`BindGame`으로 나누고, WindowManager 스택을 정렬 구분 순으로, 탭 전환은 System 밑만 닫게 바꿨다. 테스트 215개 통과(새 19개). 결과는 [UI_DESIGN.md](UI_DESIGN.md) 10-4.
- **탭 2개 이관 — UI 1차 끝 (2026-11-26):** 탭이 Exclusive 창이다(`WindowOptions.Stack`, 열릴 때 먼저 요청된 창 중 System 밑을 닫는다). 캐릭터 탭·스킬 탭은 `UIWindow` + View 인터페이스 + Presenter, 탭바는 HUD 위젯(View + Presenter)이고, `UIManager`/`UIBase`/`UITabPanel`과 UIRoot의 "이관 기간 연결"을 지웠다. 잠금은 "창이 연결된 탭만 열림"(우회 불가), 선택된 탭 강조를 넣었다. 업그레이드 "다음" 값은 진행도의 미리보기(`PreviewUpgrade`, 실제 능력치와 같은 계산)라 float 표시 API와 공식 중복이 없어졌다. 테스트 253개 통과(새 38개). 결과는 [UI_DESIGN.md](UI_DESIGN.md) 10-5.
- **UI 2차: 서비스 (2026-11-26):** 실패한 명령의 이유를 토스트로 알리고(골드 부족, 경험치 부족, "Lv.3부터 배울 수 있습니다", 잠긴 탭의 조건), 빈 스택의 뒤로가기는 종료 확인창(`await dialogs.Confirm(...)`)이다. 화면 UI의 모든 버튼이 `UIButton`(한 프레임에 클릭 하나, 소리 자리, 모양만 불가)이다. 탭은 게임 쪽 해금(엑셀 `ContentUnlockDatabase`, 저장하지 않는 파생 상태, 지금 스킬 탭 = Lv.2)을 구독하고, 레드닷(레벨업·업그레이드·배울 스킬)은 진행도의 파생 상태다. 개발자 도구에 UI 상태 표시(창 스택·입력 차단 이유). 원안의 "버튼마다 입력 차단 확인·시간 간격 연타 방지"는 시험해 보니 시스템이 이미 막고 있어 "한 프레임 하나" 규칙으로 정리했다. 테스트 299개 통과(새 46개), 사본 플레이 확인. Android 기기 확인은 하지 않았다(아래 "UI"). 결과는 [UI_DESIGN.md](UI_DESIGN.md) 10-6.
- **전투 5단계: 분리 완성 + UI 3차 어셈블리 분리 (2026-11-26~27):** 로직은 연출을 사건으로만 부르고(5-A), 순수 C# 루프가 고정 단계를 돌리며 씬 없는 실행이 플레이와 비트 단위로 같다(5-B). 그 전에 주인을 바로잡았다(12절: 게임 계층 `Game`, 전투원의 주인 = 시뮬레이션, 데이터 한 벌). 마지막으로 어셈블리 6개 `Core ← Simulation ← Game ← View ← UI ← App`로 나눴다(13절): Core·Simulation은 Unity를 참조하지 않고, 시뮬레이션은 값(`SkillSpec`, `StageSpec`, `ActionTiming`, `CombatantSpec`)만 받고, 바깥은 읽기 전용 접점만 본다. 위반은 컴파일 오류와 `ArchitectureTests`가 잡는다. 테스트 323개, 기준선 그대로, 릴리스 빌드에 개발자 도구 없음, S24 확인.
- **옛 브랜치 `UIManager_improvement`는 병합하지 않기로 결정:** `.gitignore` 규칙, `BalanceConfig`, 코드리뷰/백로그의 유효 항목만 옮겼다. UIRegistry와 Canvas 정리는 UI_DESIGN이 대체, SingletonBehaviour는 보류(아래 "코드 품질"). 집 PC에만 남은 그 브랜치의 커밋 4개와 stash는 **이어가는 데 필요 없다.**

### 5. 사용자 결정/확인 대기

- **슬라임(1001) 처치 보상 골드 10000, 경험치 100**이 테스트용으로 남은 값인지(예전 JSON은 111, 0. 지금 원본 엑셀은 `.asset` 값을 따랐다).
- **BossUndead(2002) HP 1000 → 10000**을 반영할지. `origin/UIManager_improvement`의 `3c15d5e`에 섞여 있어 일부러 가져오지 않았다.
- **(WebGL 데모를 낼 때) 웹에서 체크포인트 사이 진행 유실**을 어떻게 막을지. "주기적 자동저장은 두지 않는다"는 기존 결정(CLAUDE.md)과 부딪힐 수 있다.
- **보스전 제한 시간 값(D25).** 구조는 들어가 있고(엑셀 `StageDatabase.bossTimeLimit`, 0 = 없음) 지금 모든 스테이지가 0이다. 몇 초로 할지, 넘겼을 때 지금처럼 스테이지를 처음부터 할지는 게임 디자인 결정이다. 0이면 보스전이 끝난다는 보장이 없다(보스 회복이 플레이어 피해를 넘으면 계속된다).
- **Android 렌더 프레임률을 올릴지.** 코드에 `Application.targetFrameRate` 설정이 없어 Unity 모바일 기본값(30fps로 알고 있음, 기기에서 미측정)으로 그린다. 이 상태에서 S24 화면의 움직임은 매끄럽다(사용자 확인, 2026-11-23). 60/120으로 올릴지는 배터리와의 선택.
- **에디터에서 직접 플레이한 눈 확인.** 업그레이드 비용, 골드 HUD, 스킬 창은 Claude가 WebGL 화면으로만 봤다(Android에서는 첫 빌드가 실행돼 전투, HUD, 탭바가 도는 것까지만 확인).

- **(해결, 2026-11-25) `BossChallengeButton` ↔ `GameManager` 양방향 참조, 버튼이 상태와 어긋나는 버그.**
  예전에는 버튼이 스스로 `Hide()`하고 `GameManager.EnterBossBattle()`을 직접 불렀고, 도전 가능 상태에서 죽거나 개발자 도구로 옮기면 버튼이 남아 누르면 보스전이 시작됐다.
  전투 4-A에서 버튼은 View + Presenter가 됐다: 보이기는 흐름의 상태(`EncounterDirector.BossChallengeAvailable`) 하나가 정하고, 누르면 명령(`RequestBossChallenge`)이 받을 수 있는지 검사해 결과를 돌려준다. 회귀 테스트 `EncounterDirectorTests.BossChallengeAvailable_ThenWipe_TurnsOffAndRejectsRequest`([COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 10-9).

- **(해결, 2026-11-26) 탭 잠금 규칙이 탭바에만 있었음.**

## 렌더링

- **월드 오브젝트의 Sorting Layer 정리**
  프로젝트의 Sorting Layer가 `Default` 하나뿐이라, 배경/캐릭터/몬스터/이펙트/월드 HP바(`HpBar.prefab`, World Space Canvas)의
  앞뒤 순서를 전부 Order in Layer 숫자 하나로 맞추고 있다. `Background → Character → WorldFx → WorldUI` 같은 Sorting Layer로 나누면
  "HP바는 항상 캐릭터 위" 같은 규칙이 숫자 맞추기가 아니라 구조로 보장된다.
  화면 UI는 Screen Space - Overlay라 Sorting Layer가 적용되지 않으므로 이 작업과 무관하다(화면 UI 순서는 코드 enum → sortingOrder 구간으로 관리).
  현재 순서가 깨지는 증상은 없어서 범위 밖으로 둠.

    씬 로드 전에 `Time.captureDeltaTime = 1f/30`. 씬 로드 후 시작한 코루틴에서 `r = new System.Random(시드)`, `yield return null` 한 번 뒤 매 프레임
    `Time.captureDeltaTime = r.Next(100) == 0 ? 1f/3 : 1f/30; yield return null;`을 반복한다. 게임 시간 40초 동안 골드가 안 늘면 정지로 본다(최대 1500초).
  - 수정 전(마지막으로 골드가 는 시각): 시드 1 = 301.57초, 2 = 312.87초, 3 = 71.43초. 수정 후: 셋 다 1500초까지 진행, 처치 272마리로 같음.
  - 전투 5-B(2026-11-27)부터 이 재현법은 EditMode 테스트다(`HeadlessGameTests.OriginalStallSeeds_NeverStop_For1500Seconds`: 같은 세이브·같은 프레임 규칙을 씬 없이 실제 데이터로, 처치 간격 40초 이하). 에디터 플레이로 잴 필요가 없다.

- **(해결, 2026-11-24) 공격속도가 빠를수록 실제 공격 간격이 늘어남.** 애니메이터 왕복(Attack → Idle → Attack)과 끝 이벤트 대기 때문에 간격 0.1초 설정이 실제 0.14초였다. 전투 1단계(행동 시간표)로 0.1초 그대로가 됐다. BossSlime이 데이터(1.0초) 대신 클립 길이(약 1.7초)에 끌려가던 것도 같이 해결됐다.

- **스킬 쿨다운을 저장하지 않음**
  앱을 다시 켜면 모든 스킬이 바로 준비된다. 쿨다운이 긴 스킬이 생기면 껐다 켜는 것으로 악용할 수 있다. 저장하려면 세이브 형식에 필드를 더해야 해서(CLAUDE.md "저장" 주의사항) 오프라인 보상의 마지막 저장 시각과 함께 설계한다.

- **(해결, 2026-11-25) 스크롤이 "달리기 상태의 몬스터가 스스로 이동"으로 구현돼 있음.** 스크롤에 참여하지 않는 것(시체, 보상 동전, 이펙트)이 화면에 붙어 보였고(동전은 사용자 관찰), 보스 사거리가 플레이어보다 길면 교착이 생길 수 있었다. 전투 3단계에서 플레이어가 월드에서 실제로 전진하고 카메라가 따라가는 구조로 바꿨다. 가만히 있는 것은 이제 그냥 지나가고, 보스 사거리를 늘려도 플레이어가 다가간다([COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 9-7).

- **(해결, 2026-11-24) 타겟 규칙의 비대칭.** 플레이어는 앞쪽 몬스터만 찾아서, 뒤에 놓인 몬스터가 생기면 영구 정지가 되는 길이 규칙에 남아 있었다. 전투 2단계에서 대상 규칙을 "반대 팀의 가장 가까운 전투원(앞뒤 무관)" 하나로 바꿨다(`CombatWorld`, 테스트 `CombatWorldTests`).

- **(해결, 2026-11-24) BossSlime이 "느린 1~2대 + 빠른 4대"로 때림.** 기본 공격은 데이터 길이(1.0초), 스킬은 클립 길이(1.83초)라 같은 클립이 다른 속도로 재생됐고, 스킬은 공격의 해제 시점에만 끼어들었다. 행동 길이를 데이터(`castTime`)로, 순서를 "취소 없음"으로 정해 모든 행동이 1.0초 간격으로 고르게 이어진다([COMBAT_ARCHITECTURE.md](COMBAT_ARCHITECTURE.md) 7-13).

- **(해결, 2026-11-24) 스킬을 다른 슬롯으로 옮기면 쿨다운이 0이 됨.** 쿨다운을 스킬 id 기준으로 보관한다(`SkillLoadout`, 전투 1단계). 슬롯 이동, 장착 해제 후 재장착에도 유지된다(테스트 `SkillLoadoutTests`).

## 저장

- **WebGL 빌드에서 새로고침하면 세이브가 전부 사라짐** (2026-11-22 빌드로 재현)
  기본 템플릿의 `index.html`에 `config.autoSyncPersistentDataPath = true;`가 주석 처리돼 있어 `persistentDataPath`(IDBFS)가 브라우저 저장소로 내려가지 않는다.
  빌드 산출물에서 그 한 줄을 켜면 유지되는 것까지 확인했다. 빌드마다 손으로 고치지 않으려면 프로젝트 WebGL 템플릿이 필요하다.
  - 만드는 법(템플릿으로 빌드하는 것까지는 미검증): 에디터 설치 폴더의 `PlaybackEngines/WebGLSupport/BuildTools/WebGLTemplates/Base/Default`를
    `Assets/WebGLTemplates/<이름>`으로 복사 → `index.html`의 그 줄 주석 해제 → Player Settings의 WebGL Template을 그 템플릿으로(지금은 `APPLICATION:Default`).
  - 이미 만들어 배포한 WebGL 빌드에도 같은 문제가 있다. 다시 빌드해서 올려야 한다.
  별개로 웹은 새로고침/탭 닫기 때 `OnApplicationQuit`이 오지 않아 마지막 체크포인트 이후 진행(골드, 경험치)은 잃는다(31.5K → 21K로 재현).

- **골드가 10^15 이상이면 저장/로드 때 1씩 어긋날 수 있음**
  `JsonUtility`의 `double` 변환 오차다(10^15 미만은 어긋남 없음, 10^15대에서 최대 1). `GameNumber`의 정밀도 한계(약 9×10^15)보다 조금 일찍 나타난다.

- **세이브 버전과 마이그레이션 없음**
  저장 형식에 버전이 없어서 필드 이름이나 구조를 바꾸면 기존 진행도를 옮길 방법이 없다. 버전 필드와 버전별 변환 경로가 필요하다.
  오프라인 보상의 마지막 저장 시각처럼 필드를 추가할 때 함께 설계한다. 필수 키 검사를 도입한 뒤라면 새 필드가 없는 옛 세이브를 손상으로 판정하지 않아야 한다.

- **저장이 원자적이지 않고 백업이 없음**
  `LocalFileSaveStorage.Save`가 원본에 바로 덮어써서, 쓰는 도중 앱이 죽으면 파일이 잘린다.
  임시 파일에 쓴 뒤 교체하고 직전 정상본을 `.bak`으로 남긴다. 플랫폼별(WebGL, Android) 교체 동작은 확인이 필요하다.

- **손상된 세이브의 복구 수단 없음**
  손상을 감지해 멈추고 세이브 오류 창으로 알리기만 한다(2026-11-26, [UI_DESIGN.md](UI_DESIGN.md) 10-4). 창의 버튼은 "게임 종료"뿐이라 사용자는 게임을 계속할 방법이 없다. 백업으로 복구하거나, 명시적으로 확인받은 뒤 새로 시작하는 선택지가 필요하다. 그때 그 창에 버튼을 더한다.
  - 새로 시작은 손상된 원본을 지우지 않고 옆으로 옮겨 남기는 방식이어야 하고, 백업은 원자적 저장과 `.bak`(위 항목)이 먼저다.
  - "다시 시도"도 이때 같이 본다. 원인이 그대로면 결과도 같아서 단독으로는 두지 않았다.
  씬을 다시 로드하는 방식으로 만든다면 주의: 시작에 실패한 씬을 재로드하면 파괴된 `PlayerHud`가 `OnGameStarted` 구독에 남아 다음 시작을 예외로 끊는 현상이 간헐적으로 재현됐다(원인은 확정하지 못함. 지금 게임은 씬을 재로드하지 않음). 전투 4-A에서 `OnGameStarted`(정적 사건)를 없애 이 경로는 사라졌다. 남은 정적 버스 `GlobalCombatEvents`는 4-B에서 플레이 시작 때 구독자를 비운다.

- **클라우드 세이브 / 기기 이전 없음**
  저장 구현체가 로컬 파일뿐이라 재설치나 기기 변경 때 진행도를 잃는다. SERVER_DESIGN의 `ServerSaveStorage`는 업로드와 이상치 검사까지만 정해져 있고, 새 기기로 내려받는 흐름은 없다.

  `JsonDataLoader`, `PlayerSpawner.ReleasePlayer`(→ `SaveProgress` → `GameManager.Instance`)를 지웠다(12절). 그 전의 기록: `JsonDataLoader`는 씬과 코드 어디에서도 쓰이지 않는다. `Monster`의 직렬화 필드 `maxHp`/`expReward`는 `Initialize`가 덮어써서 인스펙터 값이 의미 없다.

## 게임 기능

- **오프라인 보상 없음**
  방치형의 핵심 기능(앱을 끈 동안 쌓인 보상을 다음 접속 시 지급)이 아직 없다. 마지막 저장 시각을 세이브에 남기고,
  접속 시 경과 시간으로 보상을 계산하는 게임 쪽 기능이 필요하다. UI 쪽은 시작 팝업 순서(설계 문서 6-3, 창 닫힘 대기)로 받을 자리가 있다.
  경과 시간은 기기 시계가 아니라 서버 시간 기준으로 계산하고, 코드는 실제 시각을 `IClock`을 통해서만 얻는다
  ([SERVER_DESIGN.md](SERVER_DESIGN.md) 1장 규칙 3). 서버가 없는 지금은 `IClock`의 로컬 구현으로 시작한다.
