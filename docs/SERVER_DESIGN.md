# 서버 판정 대비 설계

서버가 일부 결과를 판정하게 될 때를 대비한 구조. UI 쪽 설계는 [UI_DESIGN.md](UI_DESIGN.md)를 따른다.
**상태: 설계 확정. 대부분은 "첫 서버 기능이 들어올 때 붙일 자리와 규칙"이며, 지금 구현할 것은 6장의 일부뿐이다.** 첫 서버 기능(4차 가챠)의 상세 설계는 8장(2026-11-27 승인, 구현 전).

## 0. 전제 (현재 코드 기준)

- 재화는 골드 하나(`GoldWallet`). 유료 재화, 가챠, 결제 코드는 없다.
- 실제 시각(`DateTime` 등)을 쓰는 코드가 없다. 방치 보상 같은 시간 기반 기능이 아직 없다.
- 따라서 **지금 서버가 판정해야 할 기능은 0개**다.

## 1. 데이터 소유권: 두 구역

|  | 클라이언트 소유 | 서버 소유 |
|---|---|---|
| 데이터 | 골드, 레벨, 경험치, 스탯 업그레이드, 스킬, 스테이지 | 유료 재화, 가챠로 얻은 것, 결제 기록 (생길 때) |
| 판정 | 클라이언트 즉시 판정 | 서버 |
| UI 명령 | 동기 | 비동기 + 입력 차단 |
| 서버와 맞추는 방법 | 스냅샷 업로드 + 이상치 검사 (2장) | 명령마다 요청/응답 (3장) |

나누는 기준은 **UI가 결과를 기다려야 하는가**다.

- 업그레이드 연타처럼 자주, 빠르게 누르는 명령을 서버 응답까지 기다리게 하면 조작감이 망가진다 → 클라이언트 판정.
- 가챠/결제처럼 결과를 서버가 만들어 내는 명령은 클라이언트가 미리 알 수 없다 → 서버 판정.

방치형에서 흔한 타협(업계 일반 관행, 문서로 확인한 것은 아님): 전투로 버는 재화는 클라이언트가 판정하고 서버는 이상치만 검사, 유료 재화/가챠/결제만 서버 판정. 이 게임의 골드는 클라이언트의 자동 전투로 벌리므로, 업그레이드를 서버가 판정하려면 서버가 전투까지 계산하거나 클라이언트가 보고한 골드를 믿어야 한다. 전자는 게임 로직을 서버에 한 벌 더 만드는 일이고, 후자는 서버 판정의 보안 이득이 거의 없다.

### 규칙

1. **서버 소유 데이터는 클라이언트가 직접 바꾸지 않는다.** 서버 응답으로만 갱신한다.
2. **서버 소유 데이터를 바꾸는 명령은 서버 소유 재화만 쓴다.** 예: 가챠를 골드로 돌리게 하면 골드 차감의 판정 주체가 둘로 갈린다.
3. **시간 기반 보상(방치 보상 등)은 서버 시간을 쓴다.** 기기 시계는 사용자가 바꿀 수 있다. 코드에서 실제 시각이 필요하면 `IClock`을 통해서만 얻는다.

## 2. 클라이언트 소유 진행도: 스냅샷 업로드 + 이상치 검사

명령을 하나하나 서버에 보내지 않고 **진행도 전체(스냅샷)를 주기적으로 올린다.** 서버는 값이 말이 되는지만 검사한다.

- **업로드 시점:** 로컬 저장은 현재 체크포인트(업그레이드, 스킬, 스테이지 전환, 종료/일시정지) 그대로. 서버 업로드는 묶어서 최대 N초에 한 번 + 일시정지/종료 시. 연타마다 요청이 나가지 않게 한다.
- **서버 검사:** 직전 스냅샷과 비교한다. 예: "늘어난 골드 ≤ 경과한 서버 시간 × 그 스테이지의 최대 획득 속도".
- **거절 시:** 서버가 마지막 정상 스냅샷을 돌려준다. 클라이언트는 `GameSession.Apply(스냅샷)`으로 값을 덮어쓰고, 반응형 상태라 화면은 자동으로 따라온다. 사용자에게 안내창을 띄운다.
- **오프라인:** 로컬 저장은 계속하고, 연결되면 업로드한다.
- 명령 로그(모든 명령을 기록해 서버가 재현) 방식이 검증은 더 정밀하지만 이 규모에서는 비용이 커서 택하지 않는다.

## 3. 서버 소유: 비관적 비동기 명령

```csharp
using (inputBlocker.Acquire("Gacha"))
{
    CommandResult<GachaReward> result = await serverCommands.Send(new GachaRequest(bannerId, count), ct);
    switch (result.Status)
    {
        case CommandStatus.Success:      view.PlayReveal(result.Value); break;
        case CommandStatus.Rejected:     toast.Show(result.Reason);     break;   // 재화 부족 등
        case CommandStatus.NetworkError:
        case CommandStatus.Timeout:      dialog.Retry(...);             break;
    }
}
```

- **요청 ID:** 명령마다 고유 ID를 붙이고 재시도 때도 같은 ID를 쓴다. 서버는 이미 처리한 ID면 같은 결과를 돌려준다. 응답 유실 후 재전송으로 **재화가 두 번 빠지는 사고**를 막는다. 재시도는 `ServerCommandService`가 한 곳에서 처리한다.
- **응답에 바뀐 서버 소유 상태를 포함한다.** 응답으로 `ServerOwnedState`(반응형)를 갱신하면 화면은 자동으로 따라온다.
- **결과 상태:** `Success` / `Rejected(이유)` / `NetworkError` / `Timeout`. UI는 이유별로 안내한다. 예외로 흐름을 끊지 않는다.
- **복구 규칙:** 앱이 꺼지거나 응답이 사라졌으면, 시작 시 서버 소유 상태를 전부 다시 조회한다. 서버가 기준이므로 이것으로 충분하다. 결제는 별도로 Unity IAP의 미완료 거래 처리 흐름을 따른다(제 지식 기준, 도입 시 확인).
- **오프라인:** 이 명령들의 버튼은 비활성화하고 "연결 필요"를 표시한다.

## 4. 전체 구조

```
UI (Presenter)
  │ 동기 명령                         │ 비동기 명령
  ▼                                   ▼
GameSession (클라 소유, 반응형)        ServerCommandService (요청 ID, 재시도, 타임아웃)
  │ 스냅샷                              │                  │ 응답으로 갱신
  ▼                                   ▼                  ▼
ISaveStorage                        IGameServer       ServerOwnedState (서버 소유, 반응형)
 ├ LocalFileSaveStorage (현재)         ├ FakeGameServer (개발용)
 └ ServerSaveStorage (업로드 묶기)     └ 실제 서버 (범위 밖)
```

## 5. 가짜 서버 (FakeGameServer)

- 개발 설정에서 지연(예: 300ms), 실패율, 타임아웃을 조절한다.
- 서버 소유 상태는 로컬 세이브와 별도 파일에 보관해 실제 서버를 흉내 낸다.
- 목적: 실제 서버 없이도 비동기 경로(대기 중 상태, 실패, 재시도, 타임아웃)를 실제로 실행해 검증한다.

## 6. 지금 할 것 / 나중에 할 것

**지금 (UI_DESIGN의 0단계·1차에 포함, 비용 작음)**

1. **`GameSession.Apply(스냅샷)`은 객체를 새로 만들지 않고 값만 덮어쓴다.** Presenter들이 GameSession을 참조하고 있어서, 객체를 새로 만들면 구독이 옛 객체에 남는다. 세이브 로드도 같은 경로를 써서 로드와 롤백을 같은 코드로 만든다. GameSession 설계 자체에 관한 것이라 나중에 바꾸면 비싸다. 실행 중에 진행도를 바꾸는 입구는 `GameManager.LoadSnapshot`(검사 → 복사본 적용 → 그 스테이지 처음부터 → 저장)으로 먼저 만들었다. 개발자 도구가 첫 사용자다([DEV_TOOLS.md](DEV_TOOLS.md) T5).
2. **명령 결과 타입**(`UpgradeResult` 등, 실패 이유 포함) — UI_DESIGN 10-1에서 결정됨.
3. **시간 규칙:** 실제 시각이 필요하면 `IClock`을 통해서만 얻는다. 지금은 해당 코드가 없으므로 규칙만 둔다.
4. 1장의 소유권 규칙.

**나중에 (첫 서버 기능이 들어올 때)**

- `IGameServer` + `FakeGameServer`, `ServerCommandService`, `ServerOwnedState`와 전용 저장 DTO, `ServerSaveStorage`(업로드 묶기, 이상치 검사), 오프라인 UI.
- 도입 시점: [UI_DESIGN.md](UI_DESIGN.md) 9장 **4차(가챠)** — 서버가 판정하는 첫 기능과 함께 만든다. 상세 설계는 8장.
- 미뤄도 되는 이유: 전부 새로 추가되는 부품이라 기존 코드를 거의 고치지 않는다. 서버 소유 데이터는 새 DTO로 따로 두므로 기존 세이브를 옮길 필요가 없다.

## 7. 한계

- 클라이언트가 판정하는 골드는 메모리 변조로 조작할 수 있다. 이상치 검사는 완벽한 차단이 아니라 "말이 안 되는 값"을 걸러내는 수준이다. 랭킹 경쟁이 핵심 콘텐츠가 되면 다시 검토한다.
- 실제 서버 구현은 이 프로젝트 범위 밖이다. 가짜 서버까지만 만든다.
- (4차, 8장) 릴리스 빌드도 기기 안의 가짜 서버를 쓴다. 서버 소유 데이터가 기기의 파일에 있어 변조를 막지 못한다. 서버 상태 캐시(S4)를 고치면 오프라인 동안 보유 효과가 부풀고, 연결되면 서버 값으로 돌아온다.
- (4차, S8) 뽑기 응답을 기다리는 중에 앱이 꺼지면 그 결과 창은 다시 볼 수 없다. 보석·장비는 다음 시작의 조회로 서버와 맞는다.

## 8. 4차 상세 설계: 가챠와 서버 대비 부품 (2026-11-27 승인, 결정 8-13. 구현 전)

서버가 판정하는 첫 기능(가챠)과 그 기능이 쓰는 서버 대비 부품의 상세 설계다. 둘을 같이 만드는 이유는 [UI_DESIGN.md](UI_DESIGN.md) 9장 "4차 가챠를 따로 두는 이유"(부르는 코드가 없는 가짜 서버는 검증할 수 없다)다. 1~6장의 규칙은 그대로이고, 이 장은 그 규칙을 지금 코드(5-C 뒤, `8dd3b19`)에 어떻게 놓을지 정한다.

**이 단계가 보이는 것은 구조이지 보안이 아니다.** 진짜 서버는 범위 밖이라(7장) 릴리스 빌드도 기기 안의 가짜 서버를 쓴다. 서버 소유 데이터가 기기의 파일에 있으므로 변조를 막지 못한다. 보이는 것은 소유권의 경계, 비동기 명령, 요청 ID, 실패와 재시도, 서버 시각, 그리고 가짜 서버를 진짜로 바꿀 때 클라이언트 코드가 바뀌지 않는다는 것이다.

### 8-1. 지금 코드 점검

| 점검 | 근거(코드) | 4차에 주는 뜻 |
|---|---|---|
| 서버 소유 데이터가 없다 | 재화는 골드(`GoldWallet`) 하나. 장비·동료·상점은 탭(`UITabType`)에만 있고 "준비 중"이다. 게임 콘텐츠(`GameContent`)는 Character, Skill뿐 | 재화(보석), 결과물, 탭 콘텐츠가 모두 새로 생긴다 |
| 비동기 명령이 없다 | UI 명령은 전부 동기 + 결과(UI_DESIGN 10-1). 비동기는 창 API(`Awaitable`, `await handle.Closed`)뿐 | 서버 명령만 비동기가 된다(10-1 "그 명령만"). 결과를 기다리는 모양은 창 API와 같게 한다 |
| 입력 차단은 준비돼 있다 | `InputBlocker`: 참조 카운트, 0.3초 뒤 스피너, 10초 넘으면 경고. 창 열기와 페이드가 쓴다 | 대기 표시는 새로 만들지 않는다. 명령 하나의 최대 대기는 10초 경고보다 짧아야 한다 |
| 실제 시각 코드가 없다 | `DateTime` 사용 없음. `IClock`은 규칙만(1장 규칙 3) | 무료 보석(S2)을 하면 `IClock`의 첫 사용이 된다 |
| 저장 형식에 버전이 없다 | `PlayerSaveData`에 버전 필드가 없다. 검사기는 필수 키를 보므로 새 필드를 버전 변환 없이 필수로 만들 수 없다. `LocalFileSaveStorage.Save`는 원본에 바로 쓴다(개발자 도구 백업만 임시 파일 → 이름 바꾸기) | 새 파일이 둘 생긴다(서버 상태 캐시, 가짜 서버 DB). 처음부터 버전과 원자적 쓰기를 넣을 수 있다(S6) |
| 능력치는 한 함수다 | `PlayerStats.ComputeCombatStats` → 파생 상태 `CombatStats` → `PlayerCombat`이 구독해 전투원에 넣는다. 캐릭터 탭의 "현재 → 다음"(`PreviewUpgrade`)도 같은 함수 | 보유 효과를 그 함수의 원천 하나로 더하면 전투·HUD·캐릭터 탭이 함께 맞는다 |
| 진행도 교체는 클라이언트 소유만 | `Game.LoadSnapshot` → `GameSession.Apply` | 서버 소유 상태는 다른 입구(서버 응답)로만 바뀐다. 개발자 도구 "새로 시작"은 보석·장비를 건드리지 않는다 |
| 저장소 스위치가 정적이다 | `SaveStorageProvider.Current`(설정할 수 있는 정적) | 새 서버 부품은 이 모양을 따르지 않는다. 조립 지점(`GameInitializer`)이 만들어 넘긴다(COMBAT_ARCHITECTURE 12절 D46: 정적 조회 없음) |

### 8-2. 범위

**가챠** (8-13 결정)

| | 내용 |
|---|---|
| 뽑는 것 | 장비. 장착하지 않고 **가지고만 있어도 효과**가 있다(보유 효과: 최대 HP 또는 공격력에 더한다). 같은 장비를 또 뽑으면 개수가 늘고 효과가 쌓인다 |
| 재화 | 보석(서버 소유, 정수). 골드로는 뽑지 않는다(1장 규칙 2) |
| 상품 | 뽑기 표의 행마다 버튼 하나(예: 1회 300, 10회 2700). 10회는 요청 하나 = 차감 한 번 |
| 결과가 들어가는 곳 | 서버 소유 상태(보석, 장비별 개수) → 보유 효과 → 전투 능력치. 클라이언트 진행도(`PlayerSaveData`)는 바뀌지 않는다 |
| 보석 지급 | 계정을 처음 만들 때, 무료 보석(서버 시각 기준으로 일정 간격마다 받기, 서버 명령), 개발자 도구 |
| 화면 | 상점 탭(보석, 무료 보석, 뽑기 버튼, 확률), 결과 창, 장비 탭(보유 목록과 효과 합) |

**서버 대비 부품:** 서버 접점 `IGameServer`와 가짜 서버 `FakeGameServer`, 명령 서비스 `ServerCommandService`, 서버 소유 상태 `ServerOwnedState`와 그 저장 형식, 서버 상태 캐시(S4), 세이브 버전과 원자적 쓰기(S6), `IClock`, UI의 서버 명령 흐름(`ServerCommandFlow`).

**하지 않는 것:** 스냅샷 업로드와 이상치 검사(`ServerSaveStorage`, S7), 결제(IAP), 천장(일정 횟수 보장), 장착·강화·분해, 뽑기 기록 창, 배너 여러 개(표는 여러 행을 받지만 화면은 하나), 진짜 서버, 클라우드 세이브.

### 8-3. 데이터 (엑셀 → JSON → SO)

| 시트 | 열 | 검사 |
|---|---|---|
| `EquipmentDatabase` | `id`, `equipmentName`, `grade`(`EquipmentGrade`: Common 1, Rare 2, Epic 3), `statType`(`EquipmentStat`: MaxHp 1, Attack 2), `statValue`(장비 하나의 효과), `gachaWeight`(정수 ≥ 0, 0 = 뽑기에 나오지 않음) | 가중치 합 > 0, 효과 ≥ 0 |
| `GachaDatabase` | `id`, `productName`, `pullCount`(≥ 1), `gemCost`(≥ 1) | 행이 하나 이상 |
| `ContentUnlockDatabase` | 행 둘 추가: Shop(3), Equipment(4) | 모든 콘텐츠에 행(지금 규칙) |

- 행 클래스·표·Syncer는 지금 패턴 그대로다(`Assets/Scripts/Game/Data/`, `Assets/Editor/DataImporter/`). enum 번호는 `.asset`에 정수로 저장되므로 정한 뒤 바꾸지 않는다.
- **확률은 가중치에서 계산한다**(가중치 ÷ 합). 서버의 뽑기와 화면의 확률 표시가 같은 함수(`GachaOdds`, Game)를 쓴다. 한국은 확률형 아이템의 확률 공개가 법적 의무로 알고 있어서(2024년 시행, 제 지식 기준) 표시를 범위에 넣었다.
- 클라이언트의 표는 표시와 미리 판정(보석이 모자라면 보내지 않음)용이고 판정은 서버가 한다. 표가 어긋나면(클라이언트 데이터가 옛것) 서버가 이긴다: 모르는 상품은 서버가 거절하고, 클라이언트가 모르는 장비는 효과 없이 "알 수 없는 장비"로 보인다.
- **서버 규칙 값**(처음 지급 보석, 무료 보석 양과 간격)은 엑셀이 아니라 가짜 서버 설정 에셋에 둔다. 진짜 서버라면 서버의 설정이고, 클라이언트는 그 값을 읽지 않고 응답으로 받는다.

### 8-4. 서버 소유 상태

```
ServerStateData — 응답, 캐시 파일, 가짜 서버 DB가 같은 모양
  version          형식 버전(1)
  revision         서버가 이 상태를 바꿀 때마다 +1 (long)
  gems             보석 (long)
  equipment[]      { id, count }  가진 장비만
  freeGemAmount    다음 무료 보석 양
  freeGemReadyAt   다음 무료 보석을 받을 수 있는 서버 시각(UTC, Unix 밀리초)
```

`ServerOwnedState`(Game, 반응형, UI_DESIGN 5-3의 규칙):

- 상태 `Gems`, `Equipment`(목록 통째 교체, 5-3 "모음 데이터"), `FreeGem`(양, 시각), `HasData`(캐시나 응답을 한 번이라도 받음). 파생 상태 `EquipmentBonus`(능력치별 Σ 효과 × 개수, 장비 표에서 계산).
- **바꾸는 길은 서버 응답 하나다(1장 규칙 1).** 적용 함수는 `internal`이라 같은 어셈블리의 `ServerCommandService`와 `Game`(캐시로 시작할 때)만 부른다. 화면 쪽 어셈블리에서는 컴파일되지 않는다.
- 적용은 `GameSession.Apply`와 같은 규칙이다: 객체를 새로 만들지 않고 값만 덮어쓰고, 받은 것을 복사해 쥔다(D49).
- **순서 규칙: 이번 실행에서 이미 받은 리비전보다 작은 응답은 버린다.** 시작 조회의 응답이 그 뒤에 보낸 뽑기의 응답보다 늦게 와도 옛 상태로 돌아가지 않는다. 캐시의 리비전과는 비교하지 않는다. 서버가 기준이라, 가짜 서버 DB를 지웠을 때처럼 서버 리비전이 내려가도 이번 실행의 첫 응답이 캐시를 이긴다.

### 8-5. 서버 접점과 가짜 서버

```csharp
// Game/Server. 진짜 서버로 바꿀 때 이 접점의 구현만 바뀐다.
public interface IGameServer
{
    // 요청을 보낸다. 결과는 나중에 Pump 안에서 둘 중 하나로 온다: onResponse(응답) 또는 onFailed(연결 실패).
    // 아무것도 오지 않을 수도 있다(요청이나 응답이 사라짐). 시간 제한은 부르는 쪽(ServerCommandService)이 센다.
    // 같은 요청 ID를 다시 보내면 서버는 다시 처리하지 않고 처음 응답을 그대로 돌려준다.
    void Send(ServerRequest request, Action<ServerResponse> onResponse, Action onFailed);

    // 도착한 결과를 콜백으로 낸다. 실행기가 프레임마다 부른다. Send 안에서는 콜백을 부르지 않는다(재진입 없음).
    void Pump(double realtimeSeconds);
}
```

- 요청: 요청 ID, 종류(상태 조회 / 뽑기 / 무료 보석), 상품 id. 응답: 요청 ID, 결과(받음 / 거절 + 이유), 뽑기 결과(장비 id와 처음 얻었는지), 받은 보석, **바뀐 뒤의 전체 상태**, 서버 시각. 거절에도 상태가 실린다(캐시가 낡아 보석이 모자랐다면 실제 값으로 맞춘다).
- 거절 이유: `NotEnoughGems`, `UnknownProduct`, `NotReady`(무료 보석 시각 전), `RequestMismatch`(같은 ID에 다른 내용: 코드 오류), `ServerError`.
- **가짜 서버는 요청과 응답을 JSON으로 한 번 거쳐 넘긴다.** 네트워크처럼 경계에서 복사되고(D49), 직렬화되지 않는 값이 섞이면 바로 드러난다.

**`FakeGameServer`**

| 항목 | 규칙 |
|---|---|
| 처리 시점 | 요청이 서버에 닿는 시각(보낸 시각 + 지연의 절반)에 처리하고, 응답은 보낸 시각 + 지연에 도착한다 |
| 흉내 설정 | 지연(왕복, 초), 요청 유실률, 응답 유실률(처리는 했는데 응답이 사라짐: 요청 ID가 막는 사고), 오프라인(바로 연결 실패). 개발자 도구가 실행 중에 바꾼다. 릴리스 기본값은 지연만 있고 유실은 0 |
| 난수 | 뽑기 난수와 흉내(유실) 난수를 나눈다. 유실률을 바꿔도 같은 시드의 뽑기 결과가 같다 |
| 요청 ID 기록 | 처리한 요청의 ID → 응답과 요청 내용. 최근 128개. **불변식: 클라이언트가 같은 ID를 다시 보내는 동안(한 명령의 재시도, 몇 초) 서버가 그 ID를 기억한다** |
| 서버 시각 | `IClock`(Core, 실제 시각의 유일한 입구). 앱은 UTC 시계, 테스트는 가짜 시계 |
| 저장(서버 DB) | 세이브 폴더(`SaveProfile`을 따른다)의 `fake_server.json`. 상태를 바꿀 때마다 원자적으로 쓴다. **읽지 못하면 새 계정으로 대신하지 않는다:** 고장 상태로 모든 요청을 `ServerError`로 거절하고 파일을 건드리지 않는다(세이브 원칙을 서버 DB에도) |
| 관리 명령 | 보석 지급, 서버 초기화(백업 뒤), 흉내 설정. 개발자 도구만 쓴다(서버 접점을 지나지 않는 서버 쪽 일이다). 바꾼 뒤 도구가 상태 조회를 부른다 |

### 8-6. 명령 서비스 (`ServerCommandService`)

| 항목 | 규칙 |
|---|---|
| 동시에 | 명령(뽑기, 무료 보석)은 한 번에 하나. 진행 중에 또 오면 바로 `Busy`. 상태 조회는 따로 하나까지이고 겹치면 합친다(진행 중인 것을 준다) |
| 요청 ID | 명령 하나에 하나(`Guid`, 테스트는 주입). **자동 재시도와 사용자의 "다시 시도"가 같은 ID를 쓴다.** 새 ID는 사용자가 새 명령을 누를 때만 |
| 시간 | 실제 시간(단조, `Time.realtimeSinceStartupAsDouble`을 주입). 배속(`timeScale`)·게임 정지와 무관. 시도마다 제한 시간이 있고, 넘으면 같은 ID로 자동 재시도(S5) |
| 대기 상한 | (자동 재시도 + 1) × 제한 시간 + 재시도 간격의 합. 입력 차단 경고(10초)보다 짧아야 한다(설정 검사) |
| 결과 | `CommandResult<T>`: `Success(값)`, `Rejected(이유)`, `NetworkError`, `Timeout`, `Busy`. 앞의 넷은 3장 원안이다. **`NetworkError`와 `Timeout`은 둘 다 "결과를 모른다"**(요청이 처리됐을 수 있다)라 같은 처리를 받고 문장만 다르다 |
| 응답 적용 순서 | 상태 적용(8-4 순서 규칙) → 연결 상태 → 결과 완료. 기다리던 쪽이 깨어날 때 화면 값은 이미 새 상태다 |
| 늦은 응답 | 시간 초과 뒤 같은 ID의 응답이 오면: 명령이 아직 끝나지 않았으면(재시도 중) 그 응답으로 끝난다(먼저 온 것이 이긴다). 이미 끝났으면(사용자가 취소) 상태만 적용하고 결과는 버린다 |
| 포기 | 사용자가 취소하면 명령은 그 결과(`NetworkError`/`Timeout`)로 끝나고, 서비스가 상태 조회를 한 번 보낸다(입력 차단 없이). 처리됐다면 보석·장비가 그때 맞는다 |
| 연결 상태 | `Connection`: Unknown(시작) → Online(응답을 받음) / Offline(마지막 시도가 연결 실패·시간 초과). 버튼 모양이 구독한다 |
| 서버 시각 추정 | `ServerClock`: 마지막 응답의 서버 시각 + 그 뒤 흐른 실제 시간. 무료 보석의 남은 시간과 "받을 수 있음"(레드닷)이 쓴다. 기기 시계를 쓰지 않는다(규칙 3) |
| `Tick` 순서 | 전송 `Pump`(도착한 결과를 콜백으로) → 도착한 응답 처리 → 시간 초과 판정 → 재시도 보내기. **같은 `Tick`이면 도착이 시간 초과보다 먼저다**(제한 시각에 딱 맞춰 온 응답은 받는다) |
| 기다리는 모양 | 명령은 `ServerCall<T>`을 돌려주고, `await call.Completed`로 결과를 받는다. 창의 `Closed`처럼 읽을 때마다 새 `Awaitable`을 준다(UI_DESIGN 6-3) |

### 8-7. 지금 구조와의 연결

| | 연결 |
|---|---|
| 조립(`GameInitializer.Start`) | 세이브 로드 → **캐시 로드**(S4. 읽지 못하면 경고만 남기고 빈 상태: 캐시라서) → `Game.TryCreate(데이터, 세이브, 캐시, 옵션)` → 뷰·UI → `GameRunner.Run` → `game.Begin()` → **상태 조회**. 가짜 서버와 명령 서비스도 여기서 만들어 넘긴다(정적 스위치 없음). 시작에 실패하면(세이브 오류 창) 서버 부품도 만들지 않는다 |
| 실행(`GameRunner.Update`) | 게임을 진행하기 전에 `server.Pump` → `commands.Tick`. 응답은 고정 단계 처리 밖에서 적용된다(D48, 업그레이드 명령과 같은 자리) |
| `Game` | `ServerOwnedState`를 갖고 읽기 전용으로 낸다(`Game.Server`). 씬 없는 실행과 테스트는 서버 없이 상태를 값으로 넣는다 |
| 보유 효과 → 전투 | `PlayerStats.ComputeCombatStats`의 원천에 `EquipmentBonus`를 더한다: 최대 HP = 레벨 기본 + 업그레이드 + 보유 효과, 공격력도 같다. 현재 능력치와 미리보기(캐릭터 탭)가 이 한 함수라 따로 틀리지 않는다. `PlayerCombat`은 이미 `CombatStats`를 구독하므로 고칠 것이 없다. 보유 효과가 0이면 계산이 비트 단위로 같으므로(x + 0.0 = x) 전투 기준선(`cb06dd14e3a4ad7f`)이 그대로여야 한다 |
| 저장 계기(`SaveRequested`) | 서버 소유 상태가 바뀌어도 내지 않는다(클라이언트 진행도는 그대로). 캐시는 앱이 리비전 변화를 구독해 쓴다 |
| 진행도 교체(`LoadSnapshot`) | 클라이언트 소유만 바꾼다. 개발자 도구의 "새로 시작"·"복원"은 보석·장비를 남긴다. 서버 쪽은 도구의 "서버 초기화"(백업 뒤)가 따로 한다 |
| 세이브 원칙 | 서버 소유 진행도의 원본은 서버(가짜 서버 DB)다. 캐시는 잃어도 잃는 것이 없다(다음 조회가 채운다). 서버 DB는 진짜 서버 DB처럼 다룬다: 원자적 쓰기, 읽지 못하면 고장 상태로 멈춤 |
| 해금 | `GameContent`에 Shop(3), Equipment(4). 조건은 엑셀(10-6의 규칙 그대로) |

### 8-8. 세이브 버전과 원자적 쓰기 (S6)

| 파일 | 주인 | 없을 때 | 더 새 버전일 때 |
|---|---|---|---|
| `player_save.json` | 클라이언트 진행도 | 새 데이터(지금처럼) | 시작하지 않는다. 세이브 오류 창("더 새로운 버전의 게임에서 저장된 세이브"), 파일 그대로 |
| `server_cache.json` | 서버 상태의 사본(S4) | 빈 상태로 시작 | 캐시를 쓰지 않는다(서버가 기준) |
| `fake_server.json` | 가짜 서버 DB | 새 계정(처음 지급) | 고장 상태, 파일 그대로 |

- 버전 = 형식 번호(정수, 지금 1). 읽을 때: 같음 → 그대로, 작음 → 한 단계씩 변환(v1 → v2 → …, 단계마다 순수 함수 + 테스트), 큼 → 읽지 않는다(옛 앱이 덮어쓰면 새 형식의 값이 사라진다).
- `player_save.json`의 버전 필드(`saveVersion`)는 **없으면 1**이다. 지금까지 만든 모든 세이브가 v1이다.
- 검사기(`SaveDataValidator`)는 버전마다 필수 키를 본다. 새 필드는 그 필드가 생긴 버전부터 필수다([TODO](TODO.md) "저장": 새 필드가 없는 옛 세이브를 손상으로 판정하지 않는다). 지금은 v1뿐이라 변환 함수는 없고, 틀과 "큼 → 거부"만 만든다.
- **지금 하는 이유:** "더 새 버전 거부"는 옛 앱 안에 들어 있어야 효과가 있다. 첫 형식 변경보다 먼저 나가야 그 변경을 지킨다.
- 원자적 쓰기: 임시 파일에 다 쓴 뒤 교체하고, 직전 정상본을 `.bak`으로 남긴다. 세 파일이 같은 도우미를 쓴다(`player_save.json`이 지금 원본에 바로 쓰는 것도 같이 고친다, TODO "저장"). Android에서 교체가 원자적인지는 기기에서 확인한다(TODO에 적힌 대로 아직 모른다).

| 상점 탭 `ShopTabWindow` + `ShopTabPresenter` | Tab(Exclusive) | 보석 수(데이터가 없으면 "-"), 연결 상태, 무료 보석 버튼(남은 시간은 `Tick`), 뽑기 버튼(표의 행마다), 확률(장비별 %) |
| 결과 창 `GachaResultWindow` + Presenter | ModalPopup | 뽑은 장비(등급 색, 처음 얻음 표시), 확인. 연출은 최소 |
| 장비 탭 `EquipmentTabWindow` + Presenter | Tab(Exclusive) | 뽑기 표의 장비 전부, 개수(0은 흐리게), 장비별 효과, 효과 합 |

**서버 명령의 UI 규칙은 한 곳(`ServerCommandFlow`, UI, 순수 C#)이다.** 명령마다 Presenter가 따로 짜지 않는다(1장 원칙: 같은 종류의 문제를 시스템으로).

1. 누름 → 명령 시작. `Busy`면 아무것도 하지 않는다(입력 차단 때문에 사용자 입력으로는 생기지 않는다).
2. 결과가 올 때까지 입력을 막는다(이유 `Server:<명령>`, 스피너는 0.3초 뒤, UI_DESIGN 7장). 차단은 흐름 객체가 필드로 쥐고, Presenter가 버려지면 푼다(7장 "코루틴 지역변수로 using하지 않는다").
3. `Success` → 차단을 풀고 값을 돌려준다. 성공은 알리지 않는다(10-6): 뽑기는 결과 창이 열리고, 무료 보석은 보석 수가 바뀌는 것으로 끝난다.
4. `Rejected` → 차단을 풀고 이유 문장을 토스트로(10-6): "보석이 부족합니다", "아직 받을 수 없습니다", "판매하지 않는 상품입니다", "서버 오류가 발생했습니다".
5. `NetworkError`/`Timeout`(자동 재시도 뒤) → 차단을 풀고 확인창(`dialogs.Confirm`): "서버 응답이 없습니다 / 결과를 확인하지 못했습니다. 다시 시도할까요? / 다시 시도 / 취소". 다시 시도 → 같은 요청 ID로 2번부터. 취소(뒤로가기·바깥 터치 포함, 10-6) → 서비스가 상태를 다시 조회하고 토스트 "연결되면 결과가 반영됩니다". 확인창이 떠 있는 동안은 입력 차단을 걸지 않는다(확인창이 모달이다).

**버튼 모양**(10-6 `UIButton.Available`, 모양만 불가):
- 보석 부족 → 모양만 불가. 누르면 서버에 보내지 않고 토스트 "보석이 부족합니다"(클라이언트 미리 판정, 서버와 같은 규칙. 최종 판정은 서버).
- 연결 끊김(`Offline`) → 모양만 불가 + "연결 필요". 누르면 그대로 보낸다(보내는 것이 곧 연결 확인). **3장의 "버튼을 비활성화" 원안을 바꾼다:** 꺼 두면 이유를 보일 길이 없고(10-6), 다시 연결해 볼 수단을 따로 만들어야 한다.
- 보석 데이터가 아직 없음(캐시 없음, 첫 응답 전) → 보석 수 "-", 버튼은 누를 수 있다(서버가 판정).

**탭·레드닷·뒤로가기:** `UITabType.Shop` ↔ `GameContent.Shop`, `UITabType.Equipment` ↔ `GameContent.Equipment`(짝은 UIRoot가 맺는다, 10-6). 상점 탭 레드닷 = 무료 보석을 받을 수 있음(서버 시각 추정으로 계산하고, 그 시각을 지날 때 서비스 `Tick`이 다시 계산한다). 장비 탭 레드닷은 없다. 보석 수는 상점 탭 머리에만 보인다(HUD는 이번에 건드리지 않는다). 뒤로가기는 차단 중 무시(지금 `BackNavigator`), 결과 창은 뒤로가기로 닫힌다.

### 8-10. 어셈블리 배치 (S3)

```
Core ← Simulation ← Game ← View ← UI ← App        DevTools → 전부(에디터·개발 빌드만)
                      ↖
                        FakeServer ← App, DevTools
```

| 형식 | 어셈블리 | 이유 |
|---|---|---|
| `IClock` | Core | 실제 시각의 유일한 입구(규칙 3). 엔진이 필요 없고, 서버와 이후 오프라인 보상이 같이 쓴다. 구현(`SystemClock`, UTC)은 App |
| 서버 접점 `IGameServer`, 요청·응답, `CommandResult<T>`, 거절 이유 | Game (`Game/Server/`) | 클라이언트와 서버가 같이 쓰는 약속이다. 장비·상품 표와 같은 층이고 화면을 모른다 |
| `ServerCommandService`, `ServerCall<T>`, `ServerClock`, `IServerCommands`(Presenter 시험용 접점) | Game | 요청 ID·재시도·시간 제한은 화면과 무관한 규칙이다. 응답으로 서버 상태를 바꾸는 유일한 길이라, `ServerOwnedState`의 `internal` 적용 함수를 부를 수 있는 같은 어셈블리에 둔다 |
| `ServerOwnedState`, 보유 효과 계산 | Game | 게임 규칙(능력치)이 읽는다. 적용 함수가 `internal`이라 규칙 1을 컴파일러가 강제한다 |
| `ServerStateData`와 검사기, 세이브 버전, 원자적 쓰기 도우미 | Game (`Game/Save/`) | 저장 형식과 검사가 있는 곳. App(세이브·캐시)과 FakeServer(DB)가 같이 쓴다 |
| 장비·상품 행과 표, `GachaOdds` | Game (`Game/Data/`) | 데이터 경로(엑셀 → SO) |
| `FakeGameServer`, 설정 에셋, DB 입출력 | **FakeServer**(새 어셈블리, Core·Simulation·Game 참조) | "다른 기계"를 어셈블리 경계로 둔다. App(조립)과 DevTools(관리 명령, 흉내 설정)만 참조한다. 진짜 서버로 바꿀 때 바뀌는 것은 App의 조립 한 줄이다 |
| 캐시 저장소, `SystemClock`, 조립, `Pump`/`Tick` 호출 | App | 저장소·실행·조립의 자리(지금 `LocalFileSaveStorage`, `GameRunner`) |
| `ServerCommandFlow`, 상점 탭·결과 창·장비 탭 | UI | 창 패턴(`UIWindow` + Presenter) |
| 서버 흉내 조절, 보석 지급, 서버 초기화 | DevTools | 에디터·개발 빌드만 |

- `ArchitectureTests`에 더한다: FakeServer가 참조하는 것은 Core·Simulation·Game뿐이고, FakeServer를 참조하는 것은 App·DevTools·테스트뿐이다. `ServerOwnedState`에는 공개 쓰기 API가 없다(공개 멤버는 읽기 전용 상태).
- Simulation 참조는 형식 때문이다(`GameData`의 공개 서명에 시뮬레이션 입력 형식이 있다). FakeServer는 전투를 돌리지 않는다.
- 릴리스 빌드에도 FakeServer가 들어간다(진짜 서버가 없다). 개발자 도구와 달리 define constraint가 없다.

| S4 | 서버 상태 캐시 | 캐시 파일 + 바로 시작, 뒤에서 조회 | 캐시 없음(연결 전에는 보유 효과 없음) / 캐시 + 시작 때 조회를 기다림 | 방치형은 오프라인에서도 같은 능력치로 돌아야 한다. 기다리면 연결이 나쁠 때 시작이 늦다. 대가: 캐시는 변조할 수 있다(오프라인 동안만 효과가 부풀고, 연결되면 서버 값으로 돌아온다. 7장과 같은 종류) |

| S6 | 세이브 버전·원자적 쓰기 | 세 파일 모두 버전(player_save는 없으면 1) + "더 새 버전은 읽지 않음" + 원자적 쓰기 | 새 파일 둘만(player_save는 다음 형식 변경 때) | 거부 규칙은 옛 앱에 들어 있어야 효과가 있다. 원자적 쓰기는 같은 도우미라 player_save에 더하는 비용이 작고, 유실 위험(TODO "저장") 하나를 지운다 |
| S7 | 스냅샷 업로드(`ServerSaveStorage`)·이상치 검사 | 4차에서 뺀다 | 4차에 넣는다 | 가챠가 쓰지 않는다(쓰지 않는 것은 만들지 않는다). 업로드 묶기·검사 규칙·거절 안내는 따로 설계할 크기다. 되돌리기 길(`LoadSnapshot`)은 이미 있다 |
| S8 | 기다리는 중 앱이 꺼지면 | 3장 원안: 다음 시작 때 상태 조회만 | 보내기 전에 요청을 기록하고, 다음 시작 때 같은 ID로 다시 보내 결과 창을 보여 줌 | 보석·장비는 원안으로도 맞는다(서버가 기준). 잃는 것은 결과 창 한 번이다. 기록하려면 보내기 전 쓰기가 하나 늘고 그 파일의 손상·버전도 다뤄야 한다. 한계로 적는다 |

## 9. 결정 변경 이력

| 이전 생각 | 변경 | 이유 |
|---|---|---|
| 서버 판정이 생기면 UI 명령 전체를 비동기로 | UI가 결과를 기다려야 하는 명령만 비동기 | 서버가 있어도 클라이언트 판정 + 검증(낙관적)이면 UI는 기다리지 않음 |
| 모든 명령을 데이터로 만들고 요청 ID 부여 | 서버 판정 명령에만 | 클라이언트 소유 진행도는 스냅샷으로 맞추므로 명령 로그가 필요 없음 |
| 오프라인이면 서버 명령 버튼을 비활성화(3장) | 모양만 불가 + "연결 필요", 누르면 그대로 보낸다(8-9) | UI 2차의 규칙(꺼 두면 이유를 보일 길이 없다, UI_DESIGN 10-6). 보내는 것이 곧 연결 확인이라 다시 연결해 볼 수단을 따로 만들지 않는다 |
| `NetworkError`·`Timeout`이면 바로 재시도 대화(3장 예시) | 같은 요청 ID로 자동 재시도 1번 → 확인창 → 취소면 상태 조회. 둘은 "결과를 모른다"로 같은 처리(8-6, S5) | 짧은 끊김은 사용자가 모르게 넘긴다. 취소 뒤 조회가 "처리됐는데 응답만 사라짐"을 맞춘다 |
| 첫 서버 기능과 함께 `ServerSaveStorage`(업로드 묶기, 이상치 검사)도(6장) | 4차에서 뺀다(S7) | 가챠가 쓰지 않는다. 따로 설계할 크기다 |
