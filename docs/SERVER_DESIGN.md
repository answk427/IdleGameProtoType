# 서버 판정 대비 설계

서버가 일부 결과를 판정하게 될 때를 대비한 구조. UI 쪽 설계는 [UI_DESIGN.md](UI_DESIGN.md)를 따른다.
**상태: 설계 확정. 대부분은 "첫 서버 기능이 들어올 때 붙일 자리와 규칙"이며, 지금 구현할 것은 6장의 일부뿐이다.**

## 0. 전제 (현재 코드 기준)

- 재화는 골드 하나(`GoldWallet`). 유료 재화, 가챠, 결제 코드는 없다.
- 실제 시각(`DateTime` 등)을 쓰는 코드가 없다. 방치 보상 같은 시간 기반 기능이 아직 없다.
- 따라서 **지금 서버가 판정해야 할 기능은 0개**다.

## 1. 데이터 소유권: 두 구역

|  | 클라이언트 소유 | 서버 소유 |
|---|---|---|
| 데이터 | 골드, 레벨, 경험치, 스탯 업그레이드, 스킬, 스테이지 | 유료 재화, 가챠로 얻은 것, 결제 기록 (생길 때) |
| 판정 | 클라이언트 즉시 판정 | 서버 |
| UI 명령 | 동기 | 비동기 + 입력 차단 |
| 서버와 맞추는 방법 | 스냅샷 업로드 + 이상치 검사 (2장) | 명령마다 요청/응답 (3장) |

나누는 기준은 **UI가 결과를 기다려야 하는가**다.

- 업그레이드 연타처럼 자주, 빠르게 누르는 명령을 서버 응답까지 기다리게 하면 조작감이 망가진다 → 클라이언트 판정.
- 가챠/결제처럼 결과를 서버가 만들어 내는 명령은 클라이언트가 미리 알 수 없다 → 서버 판정.

방치형에서 흔한 타협(업계 일반 관행, 문서로 확인한 것은 아님): 전투로 버는 재화는 클라이언트가 판정하고 서버는 이상치만 검사, 유료 재화/가챠/결제만 서버 판정. 이 게임의 골드는 클라이언트의 자동 전투로 벌리므로, 업그레이드를 서버가 판정하려면 서버가 전투까지 계산하거나 클라이언트가 보고한 골드를 믿어야 한다. 전자는 게임 로직을 서버에 한 벌 더 만드는 일이고, 후자는 서버 판정의 보안 이득이 거의 없다.

### 규칙

1. **서버 소유 데이터는 클라이언트가 직접 바꾸지 않는다.** 서버 응답으로만 갱신한다.
2. **서버 소유 데이터를 바꾸는 명령은 서버 소유 재화만 쓴다.** 예: 가챠를 골드로 돌리게 하면 골드 차감의 판정 주체가 둘로 갈린다.
3. **시간 기반 보상(방치 보상 등)은 서버 시간을 쓴다.** 기기 시계는 사용자가 바꿀 수 있다. 코드에서 실제 시각이 필요하면 `IClock`을 통해서만 얻는다.

## 2. 클라이언트 소유 진행도: 스냅샷 업로드 + 이상치 검사

명령을 하나하나 서버에 보내지 않고 **진행도 전체(스냅샷)를 주기적으로 올린다.** 서버는 값이 말이 되는지만 검사한다.

- **업로드 시점:** 로컬 저장은 현재 체크포인트(업그레이드, 스킬, 스테이지 전환, 종료/일시정지) 그대로. 서버 업로드는 묶어서 최대 N초에 한 번 + 일시정지/종료 시. 연타마다 요청이 나가지 않게 한다.
- **서버 검사:** 직전 스냅샷과 비교한다. 예: "늘어난 골드 ≤ 경과한 서버 시간 × 그 스테이지의 최대 획득 속도".
- **거절 시:** 서버가 마지막 정상 스냅샷을 돌려준다. 클라이언트는 `GameSession.Apply(스냅샷)`으로 값을 덮어쓰고, 반응형 상태라 화면은 자동으로 따라온다. 사용자에게 안내창을 띄운다.
- **오프라인:** 로컬 저장은 계속하고, 연결되면 업로드한다.
- 명령 로그(모든 명령을 기록해 서버가 재현) 방식이 검증은 더 정밀하지만 이 규모에서는 비용이 커서 택하지 않는다.

## 3. 서버 소유: 비관적 비동기 명령

```csharp
using (inputBlocker.Acquire("Gacha"))
{
    CommandResult<GachaReward> result = await serverCommands.Send(new GachaRequest(bannerId, count), ct);
    switch (result.Status)
    {
        case CommandStatus.Success:      view.PlayReveal(result.Value); break;
        case CommandStatus.Rejected:     toast.Show(result.Reason);     break;   // 재화 부족 등
        case CommandStatus.NetworkError:
        case CommandStatus.Timeout:      dialog.Retry(...);             break;
    }
}
```

- **요청 ID:** 명령마다 고유 ID를 붙이고 재시도 때도 같은 ID를 쓴다. 서버는 이미 처리한 ID면 같은 결과를 돌려준다. 응답 유실 후 재전송으로 **재화가 두 번 빠지는 사고**를 막는다. 재시도는 `ServerCommandService`가 한 곳에서 처리한다.
- **응답에 바뀐 서버 소유 상태를 포함한다.** 응답으로 `ServerOwnedState`(반응형)를 갱신하면 화면은 자동으로 따라온다.
- **결과 상태:** `Success` / `Rejected(이유)` / `NetworkError` / `Timeout`. UI는 이유별로 안내한다. 예외로 흐름을 끊지 않는다.
- **복구 규칙:** 앱이 꺼지거나 응답이 사라졌으면, 시작 시 서버 소유 상태를 전부 다시 조회한다. 서버가 기준이므로 이것으로 충분하다. 결제는 별도로 Unity IAP의 미완료 거래 처리 흐름을 따른다(제 지식 기준, 도입 시 확인).
- **오프라인:** 이 명령들의 버튼은 비활성화하고 "연결 필요"를 표시한다.

## 4. 전체 구조

```
UI (Presenter)
  │ 동기 명령                         │ 비동기 명령
  ▼                                   ▼
GameSession (클라 소유, 반응형)        ServerCommandService (요청 ID, 재시도, 타임아웃)
  │ 스냅샷                              │                  │ 응답으로 갱신
  ▼                                   ▼                  ▼
ISaveStorage                        IGameServer       ServerOwnedState (서버 소유, 반응형)
 ├ LocalFileSaveStorage (현재)         ├ FakeGameServer (개발용)
 └ ServerSaveStorage (업로드 묶기)     └ 실제 서버 (범위 밖)
```

## 5. 가짜 서버 (FakeGameServer)

- 개발 설정에서 지연(예: 300ms), 실패율, 타임아웃을 조절한다.
- 서버 소유 상태는 로컬 세이브와 별도 파일에 보관해 실제 서버를 흉내 낸다.
- 목적: 실제 서버 없이도 비동기 경로(대기 중 상태, 실패, 재시도, 타임아웃)를 실제로 실행해 검증한다.

## 6. 지금 할 것 / 나중에 할 것

**지금 (UI_DESIGN의 0단계·1차에 포함, 비용 작음)**

1. **`GameSession.Apply(스냅샷)`은 객체를 새로 만들지 않고 값만 덮어쓴다.** Presenter들이 GameSession을 참조하고 있어서, 객체를 새로 만들면 구독이 옛 객체에 남는다. 세이브 로드도 같은 경로를 써서 로드와 롤백을 같은 코드로 만든다. GameSession 설계 자체에 관한 것이라 나중에 바꾸면 비싸다.
2. **명령 결과 타입**(`UpgradeResult` 등, 실패 이유 포함) — UI_DESIGN 10-1에서 결정됨.
3. **시간 규칙:** 실제 시각이 필요하면 `IClock`을 통해서만 얻는다. 지금은 해당 코드가 없으므로 규칙만 둔다.
4. 1장의 소유권 규칙.

**나중에 (첫 서버 기능이 들어올 때)**

- `IGameServer` + `FakeGameServer`, `ServerCommandService`, `ServerOwnedState`와 전용 저장 DTO, `ServerSaveStorage`(업로드 묶기, 이상치 검사), 오프라인 UI.
- 도입 시점: [UI_DESIGN.md](UI_DESIGN.md) 9장 **4차(가챠)** — 서버가 판정하는 첫 기능과 함께 만든다.
- 미뤄도 되는 이유: 전부 새로 추가되는 부품이라 기존 코드를 거의 고치지 않는다. 서버 소유 데이터는 새 DTO로 따로 두므로 기존 세이브를 옮길 필요가 없다.

## 7. 한계

- 클라이언트가 판정하는 골드는 메모리 변조로 조작할 수 있다. 이상치 검사는 완벽한 차단이 아니라 "말이 안 되는 값"을 걸러내는 수준이다. 랭킹 경쟁이 핵심 콘텐츠가 되면 다시 검토한다.
- 실제 서버 구현은 이 프로젝트 범위 밖이다. 가짜 서버까지만 만든다.

## 8. 결정 변경 이력

| 이전 생각 | 변경 | 이유 |
|---|---|---|
| 서버 판정이 생기면 UI 명령 전체를 비동기로 | UI가 결과를 기다려야 하는 명령만 비동기 | 서버가 있어도 클라이언트 판정 + 검증(낙관적)이면 UI는 기다리지 않음 |
| 모든 명령을 데이터로 만들고 요청 ID 부여 | 서버 판정 명령에만 | 클라이언트 소유 진행도는 스냅샷으로 맞추므로 명령 로그가 필요 없음 |
