# 전투·애니메이션 구조 설계 (백지 기준)

상태: **초안 (2026-11-23).** 결정 D2·D3·D5·D6·D7은 추천안으로 확정했다(5-D). D4(공격속도 수식)는 별도 결정 대기. 전체 계획 안의 시기(6절)는 2026-11-24 승인. **1단계 구현·검증 완료(2026-11-24, 7절). 시간 처리는 7-11 구조로 다시 만들었다(결과 7-12).** **2단계(전투원 통합) 구현·검증 완료(2026-11-24, 8절, 결과 8-11).** 다음은 3단계(공간 모델).

이 문서는 전투와 애니메이션을 처음 설계한다고 보고 다시 짠 목표 구조다. 지금 코드는 참고만 했다.
- 문제는 "지금 수치에서 괜찮은가"가 아니라 **"어떤 데이터와 설정에서도 성립하는가"**로 판단한다.
- 지금 구조에서 남길 것과 바꿀 것은 4절, 옮겨 가는 순서는 5절에 있다.
- [COMBAT_DESIGN.md](COMBAT_DESIGN.md)는 고정 타임스텝 수정의 기록이다. 그 문서 8절(기본 공격 박자 초안)은 이 문서로 대체한다.

## 1. 요구사항: 구조가 보장해야 할 것

| | 보장 | 근거 |
|---|---|---|
| R1 | 전투 결과는 데이터(스탯, 행동 정의)와 입력만으로 정해진다. 프레임률, 애니메이터 설정, 연출과 무관하다 | 공정성, 재현, 밸런스 계산 |
| R2 | 스탯은 설정한 그대로 효과를 낸다. 공격 간격이 X면 실제로도 X다. 값의 범위에 제한이 없다(아주 빠른 공격속도 포함) | 업그레이드가 표시한 만큼 강해져야 한다 |
| R3 | 연출(애니메이션, 이펙트, 숫자)을 바꾸거나 빼도 전투 결과가 바뀌지 않는다 | 아트 교체가 데미지를 없애면 안 된다 |
| R4 | 진행이 멈추는 상태가 구조적으로 없다. 모든 대기에는 끝이 있고, 살아 있는 적은 언제나 공격할 수 있다 | 방치형은 보는 사람이 없을 때 돈다 |
| R5 | 확장: 동료(파티), 원거리 공격과 투사체, 일반 몬스터의 공격, 버프와 크리티컬(난수), 배속, 오프라인 보상 | 하단 탭(동료, 장비), `TODO.md` "오프라인 보상 없음" |
| R6 | 모바일 성능: 전투 진행 중 할당이 없고, 개체 수가 늘어도 비용이 선형이다 | GC 끊김 |
| R7 | 전투 로직을 씬과 화면 없이 돌릴 수 있다(헤드리스) | 재현 검증, 빠른 감기, 오프라인 보상 근사 |

## 2. 현재 구조 점검

문제를 원인 구조별로 묶었다. 증상 하나하나가 아니라, 같은 원인에서 앞으로도 생길 문제까지 포함한다.

### P1. 전투 규칙을 애니메이션이 정한다

- **타격 시점과 행동 종료를 애니메이션 이벤트가 정한다.** 타격은 `AE_OnHit`, 종료는 `AE_OnAttackEnd → isAnimationFinished`다. 그래서 다음 공격 시점에 애니메이터 전이(종료 시간 0.95, Idle 왕복)와 이벤트 처리 순서가 끼어든다.
  - 플레이어 공격 간격은 "설정값 + 애니메이터 왕복"이 되어 R2를 어긴다. 간격이 짧을수록 차이가 커진다. 간격 0.1초(스탯 하한)에서 실제 0.14초로 측정했다. 지금 업그레이드 상한(29회)으로는 간격이 0.42초까지만 내려가지만, 상한은 데이터라 언제든 바뀐다.
- **보스는 재생 속도를 간격에 맞추지 않아서 데이터상 간격이 무시된다.** BossSlime은 데이터 1.0초인데 클립이 1.83초라 실제로는 약 1.7초마다 공격한다. 공격력, 간격 데이터가 클립 길이에 진다.
- **스킬 시전 시간은 클립 길이다.** 데이터에 없어서 밸런스가 아트 작업에 묶인다.
- **애니메이터가 이벤트를 못 내면 전투가 멈춘다.** 이벤트가 안 오면 `isAnimationFinished`가 영원히 false다. 원인은 클립 교체, 전이 수정, 컬링 모드 변경 등이다. 지금은 컬링 모드가 모두 AlwaysAnimate(0)라 안 생기지만, 성능 때문에 컬링을 켜는 순간 생긴다. 설정 하나가 진행 정지로 이어지는 구조다(R4 위반 가능).
- **애니메이터 없이 전투를 돌릴 수 없다**(R7 불가). 고정 타임스텝 작업 때 애니메이터를 Fixed 모드로 바꾼 것도 이 의존 때문이었다.

### P2. 같은 개념이 객체마다 따로 구현돼 있다

- **플레이어와 보스의 전투 상태가 거의 같은 코드로 두 벌이다.** `PlayerCombatState`/`BossCombatState`, `PlayerAttackState`/`BossAttackState`, `PlayerSkillState`/`BossSkillState`.
- **일반 몬스터는 공격 능력이 없다**(사거리·간격 0, 공격 상태 없음). 보스와 같은 `Monster` 계열인데 능력은 하위 클래스에서만 생긴다. 일반 몬스터에게 공격을 주려면 클래스를 바꿔야 한다.
- **거리 판정 규칙이 다섯 가지다.**

  | 판정 | 방식 |
  |---|---|
  | 교전 | 표면 거리(`CombatRangeUtility`) |
  | 대상 선택 | 앞쪽만, 중심 거리(`GetClosestMonster`) |
  | 범위 스킬 | 앞뒤, 중심 거리라 반너비 무시(`GetMonstersInRange`) |
  | 보스의 범위 판정 | 중심 거리 |
  | 인카운터 종료 | 거리 무관, 전부 |

  덩치 큰 몬스터는 기본 공격은 맞는데 범위 스킬은 빗나가는 식으로 어긋난다.
- **값의 출처가 섞여 있다.** 플레이어 사거리와 이동 속도는 프리팹 값이고, 보스 사거리는 데이터다. 몬스터와 배경은 플레이어 프리팹의 이동 속도를 빌려 쓴다. 반너비는 설정값이 없으면 스프라이트 바운드에서 계산하는데, 그 값은 애니메이션 프레임마다 달라진다.

### P3. 공간 모델이 연출 트릭에서 출발했다

- "플레이어는 제자리, 세상이 움직인다"를 **각 몬스터가 달리기 상태일 때 스스로 움직이는** 방식으로 구현했다. 그래서 스크롤에 참여하지 않는 것은 배경과 따로 논다.
  - 지금도: 시체, 공격 중인 보스, 보상 아이콘.
  - 앞으로: 새 월드 오브젝트(투사체, 동료, 드롭)가 생길 때마다 같은 버그가 반복된다.
- **보스 고유 이동 속도 개념이 없다.** 보스는 스크롤 여부와 무관하게 플레이어 속도로 다가온다.
- **교착 가능성:** 보스 사거리가 플레이어보다 길면 보스는 멈춰서 때리고, 플레이어는 제자리 달리기만 한다.

### P4. 흐름 제어가 코루틴, 정적 이벤트, UI에 흩어져 있다

- **상태 전이가 정적 이벤트로 일어난다.** 몬스터는 `OnScrollChanged`를 받아 상태를 바꾸고, 구독과 해제는 상태의 `Enter`/`Exit`에 의존한다. 순서가 암묵적이고, `Exit`가 안 불리면 구독이 샌다.
- **인카운터·보스·스테이지 흐름이 다섯 곳에 나뉘어 있다.** `GameManager` 코루틴, `StageManager`, 정적 이벤트 사슬(`OnBossKilled → OnStageCleared → 전환`), UI 버튼(`BossChallengeButton`이 `GameManager`를 직접 호출), 페이드(화면 시간).
  - 이미 드러난 버그: 보스 도전 가능 상태에서 죽으면 버튼과 상태가 어긋난다(`TODO.md`).
- **진행 보장이 구조에 없다.** 인카운터는 "모든 몬스터가 죽어야" 끝나는데, 대상 선택은 앞쪽만 본다. 도달할 수 없는 몬스터가 하나라도 생기면 영구 대기다. 지금은 CCD로 그 경로를 막았지만 규칙 자체는 비대칭으로 남아 있다.

### P5. 시간, 난수, 할당

- **시뮬레이션 시간이 Unity 전역 시간에 묶여 있다.** "Tick 안의 `Time.deltaTime`은 0.02"라는 암묵 규칙이라, Unity 밖에서는 돌릴 수 없다(R7). 같은 이유로 배속을 시뮬레이션 단위로 걸 수 없다.
- **로직에 쓸 난수 출처가 없다.** 크리티컬을 넣으면 `UnityEngine.Random`(연출도 같이 쓰는 전역)을 쓰게 될 위치다. 그러면 결정성이 깨진다.
- **전투 중 할당이 잦다.** 상태 전이마다 `new`(처치할 때마다, 공격 상태로 돌아갈 때마다), 범위 판정마다 `new List`, 타격마다 배열.

### P6. 수치 모델

- **HP와 데미지가 `int`인데 성장은 지수다.** 몬스터 HP 배율이 `1.15^스테이지`라, BossSlime(기본 3000)은 스테이지 약 97에서 `int` 범위를 넘는다. 그 순간 `Mathf.RoundToInt`가 넘쳐 HP가 음수나 엉뚱한 값이 된다. 골드는 이미 `GameNumber`로 옮겼는데 전투 수치는 그대로다.
- **공격속도를 "간격에서 고정값 빼기 + 하한 0.1"로 계산한다.**
  - 업그레이드 1회의 체감 효과가 들쭉날쭉하다(간격 1.0→0.98은 2%, 0.44→0.42는 4.8%).
  - 하한에 닿으면 효과가 갑자기 0이 된다.
  - 업그레이드 상한(29회)과 스탯 하한(0.1)이 서로 모르는 두 제한이다. 지금은 상한이 먼저 걸려 하한이 쓰이지 않을 뿐이다.

### P7. 로직이 연출을 직접 부른다

- 전투 상태가 `CombatEffectManager.SpawnHitParticle`, `PlayVfx`, `AudioSource.PlayClipAtPoint`를 직접 호출한다. 데미지 숫자 색은 `target is PlayerController`로 정한다. 로직이 화면 구성 요소를 알고 있어서, 연출을 바꾸려면 전투 코드를 고쳐야 한다.

## 3. 목표 구조

### 3-1. 큰 그림: 시뮬레이션과 표현의 분리

```
          명령(보스 도전, 스킬 탭)                    이벤트(행동 시작, 타격, 피해, 사망, 원점 이동 …)
 UI ───────────────────────────▶  CombatWorld  ───────────────────────────────────────▶  Views
                                 (순수 C#, 고정 단계)                                     (MonoBehaviour)
                                        ▲                                                  │
                                        │ Tick(0.02) × n                                   │ 매 화면 프레임:
                                 CombatSimulation (드라이버)                               │ 상태 스냅숏 + 보간
                                 FixedUpdate, 배속, 이벤트 배달  ◀─────────────────────────┘
```

- **CombatWorld(순수 C#):** 전투의 모든 상태와 규칙을 갖는다. `UnityEngine` 오브젝트를 참조하지 않는다(위치는 `float x`). `Tick(dt)`로만 진행하고, 바깥으로는 이벤트만 낸다.
- **Views(MonoBehaviour):** 캐릭터 뷰(스프라이트, 애니메이터, HP바), 월드 뷰(카메라, 배경), 이펙트 뷰(데미지 숫자, 파티클, 보상). 이벤트와 상태를 읽어 그리기만 하고, 시뮬레이션을 바꾸지 않는다.
- **CombatSimulation(드라이버):** 지금 있는 클래스를 이 역할로 줄인다. `FixedUpdate`에서 월드를 진행하고, 쌓인 이벤트를 뷰에 배달하고, 화면 프레임에서는 보간 비율을 준다.
- 이 프로젝트 UI의 원칙(View + 순수 C# Presenter, UI_DESIGN)과 같은 원리를 전투에 적용하는 것이다. R1, R3, R7은 이 분리에서 나온다.

### 3-2. 공간: 1차원 월드 좌표와 카메라

- **모든 개체는 월드 x 하나로 위치를 가진다**(레인 하나). 아군(플레이어, 나중에 동료)이 실제로 전진하고, 카메라가 아군을 따라간다. 배경 오프셋은 카메라 x에서 계산한다(패럴랙스).
  - 정지한 것(시체, 보상, 서 있는 적)은 아무 등록 없이 정지해 보인다. 새 월드 오브젝트의 기본 동작이 맞는 쪽이 된다(P3 해결).
  - "스크롤 중" 상태와 그 이벤트가 사라진다.
- **이동은 sweep이다(CCD가 이동 규칙 자체).**
  - 아군 대열의 이동량은 `min(속도 × dt, 앞 적의 몸까지 거리)`다. 적이 스스로 움직일 때(보스 접근, 돌진)도 같은 함수로 아군 몸까지만 간다.
  - 단계 크기, 속도와 상관없이 몸을 통과하지 않는다.
- **원점 재설정(floating origin):** x가 계속 커지면 float 정밀도가 떨어진다(하루 방치하면 약 30만 유닛, 0.03 단위로 떨림). 그래서 인카운터를 시작할 때마다 모든 x와 카메라에서 같은 값을 빼고 `OriginShifted` 이벤트를 낸다. 뷰는 보간 기준도 같이 옮긴다.
- **몸 크기(반너비)는 데이터의 필수값이다.** 스프라이트 바운드 자동 계산은 쓰지 않는다(프레임마다 변하는 값을 판정에 쓰지 않는다).

### 3-3. 전투원(Combatant): 모델 하나

- 플레이어, 동료, 일반 몬스터, 보스는 모두 같은 `Combatant`다. 구성은 다음과 같다.
  - 팀, 위치, 반너비
  - 스탯(HP, 공격력, 공격속도, 이동 속도, 사거리)과 수정자(버프, 장비. 지금은 단순 합산으로 시작)
  - 행동 슬롯: 기본 공격 1개 + 스킬. 쿨다운은 **행동 id 기준**이다(`TODO.md`의 쿨다운 초기화 버그도 여기서 해결)
  - 두뇌 정책
- **두뇌(AI 정책)는 "다음에 무엇을 할지"만 정한다.** 규칙 한 벌을 모두가 공유하고 파라미터만 다르다.
  - 기본 규칙: 사거리 안에 대상이 있으면 준비된 행동 중 우선순위가 높은 것을 쓰고, 없으면 전진하거나 대기한다.
  - 플레이어는 "전진함", 일반 몬스터는 "제자리", 보스는 "접근함"이다. 일반 몬스터가 공격하느냐는 데이터(기본 공격 행동이 있느냐)로 정한다.
- **결정 시점은 둘이다.** 행동이 없을 때, 그리고 현재 행동이 "취소 가능" 지점에 왔을 때.

### 3-4. 행동(Action): 데이터로 정의한 시간표

**정의(ActionDef):**

| 항목 | 뜻 |
|---|---|
| 기본 길이 | 속도 1일 때 행동 한 번의 길이(초) |
| 타격 시점 | 길이에 대한 비율. 여러 번 가능(다단 히트) |
| 취소 가능 시점 | 후딜 시작(비율). 여기부터 다른 행동으로 넘어갈 수 있다 |
| 공격속도 적용 | 기본 공격은 예, 스킬은 데이터로 정한다 |
| 효과 | 데미지 배율, 범위, 힐 등. 지금의 `ISkillBehavior`를 효과 실행기로 재사용한다 |
| 쿨다운, 사거리 | |
| 연출 키 | 애니메이션 상태 이름, VFX와 SFX 참조. 시뮬레이션은 키만 들고 뷰가 해석한다 |

**실행(ActionRunner):**
- 실제 길이 = 기본 길이 ÷ 공격속도. 타격과 취소 시점은 비율이라 같이 줄어든다.
- 시간은 타이머 하나로 흐른다. 타격 시점을 지나면 효과를 적용하고, 끝에 닿으면 완료한다.
- **한 단계 안에서 행동 경계를 넘는다.** 0.02초 단계 안에서 행동이 끝나면, 남은 시간으로 다음 결정과 다음 행동을 이어서 진행한다(누산기 방식). 그래서 다음 행동은 완료 즉시 시작한다. 단계 길이보다 짧은 행동(초당 50회 이상 공격)도 정확하다(R2, 값 범위 무관).
  - 길이 0인 행동은 무한 반복이 되므로 로드할 때 막는다(최소 길이 검사). 한 단계 안 반복 횟수에도 상한을 두고, 넘으면 에러를 낸다.
- **"공격 간격"의 정의:** 기본 공격 한 번 = 행동 한 번 = `1 / 공격속도`초다. 지금의 "타이머 + 애니메이션 끝" 두 조건이 하나로 줄어든다.
- **타격 시점의 대상 재확인(결정 D3):** 단일 대상 타격 시점에 원래 대상이 죽었거나 사거리 밖이면, 사거리 안 가장 가까운 적에게 다시 정한다. 그런 적도 없으면 헛친다.
- **같은 단계 안의 순서:** 아군 → 적 순으로, 각 팀 안에서는 생성 순서대로 처리한다. 앞에서 죽은 전투원은 그 단계에서 행동하지 않는다. 동시 타격의 결과가 매번 같다.

### 3-5. 애니메이션: 시간표를 보여 주는 재생기

- **뷰가 `ActionStarted(행동, 실제 길이)` 이벤트를 받으면 해당 상태를 처음부터 재생한다.** 재생 속도는 `클립 길이 ÷ 실제 길이`다. 이동 상태(대기/달리기)와 사망은 시뮬레이션 상태를 보고 뷰가 정한다.
- **애니메이터 컨트롤러는 조건 전이 없는 상태 모음으로 단순화한다.** `Play`/`CrossFade`만 쓴다. 종료 시간, 트리거 왕복이 게임 규칙에 끼어들 자리를 없앤다.
- **Animator Update Mode는 Normal로 되돌린다.** 로직이 애니메이션을 읽지 않으므로 화면 프레임에 맞춰 부드럽게 돌아도 된다. 같은 이유로 컬링 모드도 전투와 무관해진다(성능 때문에 켜도 된다).
- **애니메이션 이벤트는 저작 수단으로만 쓴다(결정 D2).**
  - 디자이너는 지금처럼 클립에 타격(`AE_OnHit`)과 후딜 시작 지점을 찍는다. 에디터 임포터가 그것을 `클립 길이`로 나눠 ActionDef의 타격·취소 비율로 굽는다. 런타임은 클립 이벤트를 읽지 않는다.
  - 굽는 시점에 `0 < 타격 ≤ 취소 ≤ 1`을 검사해 어긋나면 에러를 낸다.
  - 클립을 고친 뒤 굽기를 잊으면 숫자와 그림이 어긋난다. 그래서 ActionDef에 구운 당시의 클립 길이와 이벤트 값을 같이 저장한다. 에디터가 열리거나 빌드할 때 현재 클립과 비교해서, 다르면 에러를 낸다.
- **표현 오차:** 타격 숫자와 이펙트는 시뮬레이션 시각에 뜨고, 캐릭터는 보간 때문에 최대 0.02초 늦게 그려진다. 사람이 구별할 수 없는 크기다. 아주 빠른 공격(화면 프레임보다 짧은 행동)은 매번 처음부터 재생돼 빠르게 휘두르는 것처럼 보인다.
- 대안(Playables API로 클립 직접 재생)은 컨트롤러를 아예 없앨 수 있지만, 아티스트가 익숙한 Animator 창을 버리게 된다. 스프라이트 플립북 규모에서는 이득이 작아서 택하지 않는다.

### 3-6. 거리와 대상: 규칙 하나

- **모든 판정은 표면 거리 하나로 한다**(교전, 단일 대상, 범위). 중심 거리 판정을 없앤다.
- **대상은 "반대 팀, 살아 있음, 표면 거리가 가장 가까움"이다.** 앞뒤를 구분하지 않는다.
- **진행 보장(R4)은 불변식 두 개로 성립한다.**
  1. 살아 있는 적은 언제나 아군 대열 앞에 있다. 스폰은 대열 앞에만 하고, 이동은 sweep이라 통과가 없다.
  2. 대상 규칙은 살아 있는 모든 적을 고를 수 있다.

  그러면 인카운터 종료 조건 "살아 있는 적 0"에는 언제나 도달할 수 있다. 1번은 시뮬레이션 단계 끝에 개발 빌드 전용 검사로 확인한다.

### 3-7. 흐름: 시뮬레이션 안의 상태 기계

- **EncounterDirector(시뮬레이션 안, 고정 단계로 진행)가 흐름을 소유한다.** 상태는 다음과 같다.
  - 이동 → 교전 → 정리 대기(n초) → 다음 인카운터
  - 보스 도전 가능 → 보스 등장 → 보스전
  - 스테이지 클리어 / 아군 전멸 → 전환(n초) → 새 스테이지
- **UI는 명령만 넣는다.** 보스 도전 버튼은 `RequestBossChallenge` 명령을 넣고, 디렉터는 가능한 상태일 때만 받는다. 버튼 표시는 디렉터 상태를 구독한다. 보스 도전 버튼이 상태와 어긋나는 버그가 구조적으로 사라진다.
- **전환 시간은 시뮬레이션 상수다.** 페이드는 뷰가 그 시간에 맞춰 그리기만 하고, 시뮬레이션은 화면을 기다리지 않는다. 그래서 스테이지 전환까지 결정적이다(지금 남은 "페이드는 화면 시간" 한계 해소).
- **모든 대기 상태에는 끝이 있다.** 디렉터는 개발 빌드에서 "일정 시간 동안 진전 없음"(데미지 0, 이동 0)을 감시해 경고한다. 진행 정지가 생기면 숨지 않고 드러난다.
- 정적 이벤트 버스(`GlobalGameEvents`)는 시뮬레이션 → 바깥(저장, UI 알림) 방향으로만 남기고, 흐름 제어에는 쓰지 않는다.

### 3-8. 시간, 난수, 배속, 수치

- **시뮬레이션은 자기 시계(틱 수)를 갖고 dt를 인자로 받는다.** `Time.deltaTime`을 쓰지 않는다.
- **로직용 난수는 시뮬레이션이 소유한다**(시드 있는 난수). 연출용 난수(보상 아이콘 흩뿌림)는 따로 둔다.
- **배속은 드라이버가 한 `FixedUpdate`에서 월드를 n번 Tick한다(결정 D6).** `Time.timeScale`을 건드리지 않으므로 UI 연출과 트윈은 배속의 영향을 받지 않는다.
- **HP와 데미지는 `GameNumber`(double)다**(P6, 결정 D5: 2단계에서). 저장 DTO와 데이터 테이블의 원칙(구조체를 직렬화하지 않음)은 골드와 같다.
- **오프라인 보상:** 행동이 데이터라서 헤드리스 빠른 감기도, 통계 근사(초당 처치 수 계산)도 가능해진다. 방식은 그 기능을 만들 때 정한다.

### 3-9. 성능 규칙

- 상태와 행동 인스턴스는 재사용한다(전투원마다 미리 만들어 둔다). 목록은 버퍼를 재사용하고, 이벤트는 구조체 버퍼로 모은다. **Tick 중 할당 0**이 목표이고, 개발 빌드에서 Profiler 마커로 확인한다.
- 뷰는 지금처럼 풀링한다(`PoolManager`).

## 5. 옮겨 가는 순서

각 단계가 끝날 때마다 게임은 그대로 돌고, 검증을 통과한 상태로 커밋한다.

| 단계 | 내용 | 해결 | 크기 |
|---|---|---|---|
| **1. 행동 시간표** | ActionDef와 ActionRunner(순수 C#), 이벤트 굽기 임포터와 오래된 굽기 검사, 애니메이터를 재생기로(Normal 모드, 조건 전이 제거), 스킬 쿨다운을 스킬 id 기준으로. 우선 지금 상태 클래스 안에서 ActionRunner를 쓴다 | P1. 공격속도 정확(모든 값), 보스 간격 데이터대로, 스킬 시간 데이터화, 쿨다운 초기화 버그(`TODO.md` 다음 작업 1번) | 중 |
| **2. 전투원 통합** | Combatant + 두뇌로 플레이어·보스·일반 몬스터 통일, 거리 규칙 하나, 대상 규칙 대칭, HP·데미지 `GameNumber`, 할당 제거, 로직용 난수 | P2, P5 일부, P6 | 대 |
| **3. 공간 모델** | 월드 x + 카메라 + 원점 재설정, sweep 이동, 스크롤 제거, 배경 패럴랙스 | P3 | 중 |
| **4. 흐름** | EncounterDirector, 보스 도전 명령, 전환 시간 상수화, 정적 이벤트 정리, 진전 감시 | P4, 남은 P5(시간 결정성) | 중 |
| **5. 분리 완성** | 시뮬레이션에서 `UnityEngine` 의존 제거, 이벤트로만 뷰와 연결 | P7, R7 | 중 |

- 1단계를 먼저 하는 이유: 가장 깊은 결합(P1)이고, 사용자에게 보이는 밸런스 문제를 고치며, 다른 단계에 의존하지 않는다.
- 2단계 이후 순서는 바꿀 수 있다.
- 공격속도 스탯 수식(P6 두 번째 항목)은 밸런스 결정이라 단계와 별도로 정한다(5-D4).

### 각 단계 공통 검증

지금 수치에서 통과하는 것만으로는 부족하다. **극단값으로 불변식을 확인한다.**

| 검증 | 방법 | 수단 |
|---|---|---|
| R2 공격속도 | 공격속도를 0.5 / 1 / 7 / 50 / 200회/초(단계 길이보다 짧은 값 포함)로 두고, 실제 공격 횟수 = 속도 × 시간, 타격 수 = 공격 수인지 | EditMode 테스트(1단계부터) |
| 행동 시간표 | 타격·취소 비율 경계(0, 1, 같은 값), 길이 0 거부, 한 단계 안 반복 상한, 취소 시점 전 스킬 전환 없음 | EditMode 테스트(1단계부터) |

## 7. 1단계 상세 설계: 행동 시간표 (2026-11-24 승인·구현, 결과는 7-10)

### 7-1. 범위

| 넣는 것 | 빼는 것(다음 단계) |
|---|---|
| 행동 시간표 데이터와 굽기, 오래된 굽기 검사 | 플레이어·보스 클래스 통합(2단계) |
| ActionRunner(순수 C#)와 공용 행동 결정 | 대상 규칙 대칭, 표면 거리 통일(2단계) |
| 애니메이터를 재생기로(Normal 모드, 액션 상태는 `Play`) | 이동·스크롤(3단계), 흐름(4단계) |
| 플레이어 사망 대기를 시간표로 | 이펙트·사운드 직접 호출 정리(5단계) |
| 스킬 쿨다운을 스킬 id 기준으로, 시전 시작에 시작 | HP·데미지 `GameNumber`(2단계) |
| 타격 시점 대상 재확인(D3) | 상태 객체 할당 제거(2단계) |
| EditMode 테스트 | |

1단계가 끝나면 **전투 로직이 애니메이션 이벤트와 애니메이터 전이를 하나도 읽지 않는다.**

### 7-2. 데이터

- **`ActionTimeline`(직렬화 클래스) 하나 = 캐릭터의 행동 하나.**

  | 필드 | 뜻 |
  |---|---|
  | 키 | 애니메이터 상태 이름(`Attack`, `Skill`, `Healing`, `Death`) |
  | 클립 | 원천 |
  | 구운 값 | 클립 길이, 타격 비율 목록, 해제 비율, 구울 때의 이벤트 기록(오래된 굽기 검사용) |

- **`ActionTimelineSet`(ScriptableObject) = 캐릭터 하나의 행동 목록.** `Assets/Data/Combat/Timelines/`에 플레이어(Warrior), BossSlime, BossUndead 세 개를 둔다. 일반 슬라임은 아직 행동이 없다(2단계에서 데이터로 공격을 줄 수 있게 된다).
  - 플레이어 프리팹과 보스 프리팹이 자기 세트를 참조한다.
- **타이밍은 스킬이 아니라 "시전자의 애니메이션"에 속한다.** 같은 스킬 1번을 플레이어(Dash-Attack 클립)와 BossSlime(점프 클립)이 같이 쓰기 때문이다. 그래서 `SkillData`(쿨다운, 배율, 효과)는 그대로 두고, `SkillData.AnimationTrigger` 값을 "시전자 세트에서 찾을 행동 키"로 읽는다. 필드 이름은 바꾸지 않는다(직렬화 함정). 주석만 고친다.
- **행동의 실제 길이:**

  | 행동 | 실제 길이 |
  |---|---|
  | 기본 공격 | 공격 간격(플레이어 `PlayerStats.AttackInterval`, 보스 `MonsterData.AttackInterval`). 공식은 D4 결정 전까지 지금 것 |
  | 스킬, 사망 | 구운 클립 길이. 그래서 지금과 같다 |

- **표식 이름과 의미:**

  | 표식 | 의미 | 개수 |
  |---|---|---|
  | `AE_OnHit` | 타격(효과 적용) | 행동당 1개 이상. 사망은 0개 |
  | `AE_OnAttackEnd` / `AE_OnDeathEnd` | **해제 시점.** 동작이 끝났다고 보는 지점이고, 여기부터 다른 일(스킬, 달리기 복귀, 사망 처리)로 넘어갈 수 있다 | 정확히 1개 |

  - 검사: `0 < 각 타격 ≤ 해제 ≤ 1`, 타격 비율은 오름차순.
  - **7-13에서 바뀜:** 해제 표식과 해제 비율을 없앴다(표식은 `AE_OnHit`뿐). 스킬의 길이는 클립 길이가 아니라 `SkillData.castTime`이다. 이 절과 7-3, 7-10~7-12의 "해제"는 그 전의 기록이다.
- **굽기와 검사:**
  - 메뉴 `IdleGame/Combat/Bake Action Timelines`로 굽는다.
  - 에디터를 열 때(`InitializeOnLoad`)는 현재 클립과 구운 값이 다르면 에러 로그를 낸다.
  - 빌드 직전(`IPreprocessBuildWithReport`)에는 같은 경우 빌드를 실패시킨다.
- 클립 안의 표식 이벤트는 런타임에도 애니메이터가 계속 호출한다. 그래서 뷰에 아무것도 하지 않는 수신 메서드를 둔다(없으면 "receiver 없음" 에러). 주석에 "저작용 표식, 런타임은 무시"라고 적는다.

### 7-3. 실행 (순수 C#)

- **`ActionRunner`(전투원마다 하나):** `Start(시간표, 실제 길이)`, `Advance(dt) → 남은 시간`. 진행 중에 타격(번호), 해제, 완료를 순서대로 알린다. 길이 0 이하와 비율 범위 위반은 시작할 때 막는다.
- **`CombatActions`(전투원마다 하나, 플레이어·보스 공용):** 다음에 할 행동을 정하고 러너를 돌린다. `Tick(dt)`는 남은 시간이 0이 될 때까지 다음을 반복한다(한 단계 안 반복 상한 64회, 넘으면 에러).
  - 러너가 비었거나 해제됐으면 결정한다.
    - **스킬:** 대기 중인 수동 요청 → 준비된 스킬(슬롯 순서) 순으로 고른다. 비었거나 해제된 상태에서 시작할 수 있다.
    - **기본 공격:** 러너가 완전히 끝났을 때만 시작한다. 기본 공격끼리는 공격 간격 그대로 이어진다.
  - 결정이 없으면 반복을 멈춘다.
- 시전자가 해야 할 일은 인터페이스(`ICombatActor`)로 받는다: 기본 공격 길이, 스킬 목록, 대상 찾기, 데미지 계산, 연출 훅. `PlayerController`와 `BossMonster`가 구현한다. 2단계에서 `Combatant`가 이것을 흡수한다.
- **타격 처리(D3):**
  - 기본 공격과 단일 대상 스킬은 타격 순간에 대상이 살아 있고 사거리 안인지 다시 본다.
  - 아니면 지금의 대상 규칙(플레이어는 앞쪽 가장 가까운 몬스터, 보스는 플레이어)으로 사거리 안에서 다시 찾고, 없으면 헛친다.
  - 효과는 타격 표식마다 한 번씩 실행한다(다단 히트는 표식 여러 개).
- **쿨다운은 시전 시작에 시작한다**(지금은 타격 순간). 결정 S3.

### 7-5. 애니메이션 (뷰)

### 7-11. 시간 처리 재검토: 앞선 수정은 Quick Fix였다 (2026-11-24 승인·구현, 결과 7-12)

7-10의 "결정 시점을 정밀하게 했다"는 테스트 실패(해제 뒤 대기 중 스킬이 준비됐는데 다음 단계로 밀림)를 막은 수정이었다. 다시 점검한 결과, 증상 하나를 막았을 뿐 원인 구조는 그대로라서 Quick Fix로 판정한다.

**Quick Fix인 이유**

| | 지금 구조 | 문제 |
|---|---|---|
| 1 | "결정해야 하는 순간"을 사례별로 끼워 넣었다. 해제 시점은 `ActionRunner`가 스스로 멈추고, 스킬 준비 시각은 `CombatActions`의 한 분기(해제 뒤 대기 중일 때만)에서 진행을 끊는다 | 원칙("결정에 쓰는 입력이 바뀌는 모든 순간에 결정한다")이 코드에 없다. 시간에 따라 바뀌는 입력이 하나 늘 때마다(버프 만료, 조건부 스킬 등) 같은 패치를 또 해야 한다. 이번 실패가 바로 빠진 사례 하나였다 |
| 2 | 시간 기준이 셋이다: 행동마다의 경과 시간(float), 단계 시작 기준 쿨다운 잔량(float), "단계 안에서 지난 시간"(`dt - remaining`으로 다시 계산) | 서로 빼고 더하며 오차가 생겨서, 같은 시각인데 미세하게 모자라 "아직 준비 안 됨"이 된다. 그래서 `ReadyEpsilon`(10µs)을 넣었다. 여유값은 표현 방식이 틀렸다는 증상이고, 스킬이 최대 10µs 일찍 준비된 것으로 판정된다 |
| 3 | 전투원마다 한 단계를 통째로 처리한다(플레이어 → 몬스터 순) | 같은 단계 안에서 서로 다른 전투원의 사건이 시간 순서대로 처리되지 않는다. 예: 보스가 0.005초에 플레이어를 죽이는 타격과 플레이어가 0.018초에 때리는 타격이 같은 단계에 있으면, 플레이어를 먼저 처리해서 이미 죽었어야 할 플레이어의 타격이 들어가고 보스가 먼저 죽을 수 있다. 전투원 하나 안에서는 단계 안 정밀도를 맞췄지만 전투원 사이는 단계 단위라서, 정밀도가 서로 다르다(단계 단위 문제는 1단계 전부터 있었다) |
| 4 | 시간이 암묵적이다(상태 코드 안의 `Time.deltaTime`) | 시뮬레이션 시계가 명시돼 있지 않아서 위 1~3을 한 곳에서 다룰 수 없다(3-8에서 계획만 한 것) |

**구조적 해결: 시계 하나, 절대 시각, 시간 순서 사건 처리**

1. **시뮬레이션 시계 하나**(`SimClock`, 순수 C#). 단계 번호(long)와 단계 길이(double)를 갖고, 단계 경계는 `번호 × 길이`로 계산한다(더해 가며 생기는 오차 없음). 전투의 모든 시각은 이 시계의 절대 시각(double, 초)이다. 전투 코드에서 `Time.deltaTime`을 쓰지 않고 시각과 단계를 인자로 받는다.
2. **시간을 갖는 상태는 남은 시간이 아니라 절대 시각으로 저장한다.**
   - 행동: 시작 시각, 끝 시각, 표식 시각들(`시작 + 비율 × 길이`). 시작할 때 한 번 계산해서 저장한다.
   - 스킬: 준비 시각 `readyAt = 시전 시각 + 쿨다운`. 쿨다운을 깎는 `Tick`, 단계 안 위치(offset) 인자, 여유값(`ReadyEpsilon`)이 모두 없어진다. UI는 `max(0, readyAt − 지금)`으로 표시한다.
   - **규칙: 시각은 한 번 계산해 저장하고, 다시 계산하지 않는다.** 그러면 같은 시각을 비교할 때 오차 없이 정확히 같다. 여유값이 필요 없다.
3. **사건과 결정은 하나의 원칙으로 처리한다.**
   - 전투원마다 "다음 사건 시각"을 낸다: 행동 표식(타격, 해제, 완료) + **결정 입력이 바뀌는 시각**(지금은 해제 뒤 대기 중의 스킬 준비, 대기 중인 수동 요청의 준비).
   - 결정 입력의 원천은 시전자 인터페이스의 함수 하나(`NextDecisionInputChange(지금)`)로 모은다. 버프 같은 새 입력이 생기면 이 함수만 늘린다. 반복문에 사례를 끼워 넣지 않는다.
   - 해제 시점에서 멈추는 일은 `ActionRunner`의 특별 동작이 아니라 "해제도 사건"이라서 자연히 된다.
4. **단계 안에서 모든 전투원의 사건을 시간 순서로 처리한다**(`CombatScheduler`).
   - 단계 [t0, t1]: 지금 = t0에서 교전 중인 전투원 모두 결정 → `t = 모든 전투원의 다음 사건 시각 중 최소(t1까지)` → 그 시각의 사건을 정해진 순서(플레이어 → 몬스터 생성 순)로 처리하고 결정 → 지금 = t(대입) → 반복.
   - 같은 시각의 사건은 위 순서로 처리한다(동시 사건 규칙, 문서화).
   - 사건 시각에 죽은 전투원은 그 뒤 사건을 처리하지 않는다.
   - 안전장치: 단계당 처리 상한을 두고, 넘으면 에러를 낸다. 길이 0 행동은 이미 막고 있어서, 정상적으로는 사건 시각이 늘거나 행동 수가 늘 뿐이다.
5. **시뮬레이션 단계를 국면으로 나눈다**(`CombatSimulation`).
   - ① 위치 되돌리기 → ② 전투 사건(스케줄러, [t0, t1]) → ③ 상태 전이와 이동(각 상태 기계: 달리기↔교전 전환, 몬스터 이동) → ④ 배경 → ⑤ 보간 기록 → 시계 진행.
   - 교전 상태는 시간을 진행하지 않는다. "교전 중"이라는 표시만 하고, 진행은 스케줄러가 한다.
   - ③에서 교전에 들어가면 다음 단계의 t0(같은 순간)에 첫 결정을 한다(지연 없음).
6. **정직하게 남는 경계:** 이동과 교전 시작·종료(달리기↔교전)는 단계 단위다. 이동을 단계마다 적분하는 고정 타임스텝 모델이라서 그렇다(업계 표준). 행동이 단계 중간에 끝났는데 대상이 없으면, 달리기는 그 단계 끝에 시작한다(최대 0.02초). 3단계(공간 모델)에서 sweep의 접촉 시각으로 교전 시작을 정밀화할 수 있다.

**대안과 판단**

| 대안 | 판단 |
|---|---|
| 시각을 정수(마이크로초 long)로 | 기기 사이 비트 단위 일치까지 보장된다. 하지만 행동 길이(`1 / 공격속도`)를 µs로 반올림해야 해서 설정값과 미세하게 달라진다. 2번 규칙(한 번 계산해 저장)을 지키면 double로도 같은 기기에서는 정확하므로 double을 택한다. 기기 사이 일치는 2절에서 이미 "보장하지 않음" |
| 지금 구조 유지 + 여유값 조정 | 1~4가 그대로 남는다. 기각 |

### 7-12. 결과 (2026-11-24)

### 7-13. 취소 없음, 행동 길이는 데이터가 정한다 (2026-11-24 승인·구현·검증)

**계기:** S24에서 BossSlime이 "1~2대는 느리게, 4대는 빠르게" 때리는 것처럼 보였다(사용자 관찰). 공격 패턴이 다른 것이 아니라, 길이를 정하는 규칙 둘이 섞여 있었다.
- 기본 공격의 길이는 데이터(공격 간격 1.0초)라서, 1.83초짜리 점프 클립이 1.83배속으로 재생된다.
- 스킬(강타)의 길이는 클립 길이(1.83초)라서, 같은 클립이 원래 속도로 재생된다.
- 스킬은 공격의 해제 시점에만 끼어들 수 있었다. 그래서 겉보기 순환이 "느린 스킬 1번 + 빠른 공격 여러 번"이었다.

**규칙**
1. **취소 없음.** 모든 행동(기본 공격, 스킬)은 끝까지 한다. 다음 행동은 지금 행동이 완료된 시각에 정한다. 어떤 행동도 다른 행동을 끊지 못하고, 행동을 끊는 것은 사망과 교전 종료(강제 중단)뿐이다.
2. **행동의 길이는 게임 데이터가 정한다.** 기본 공격 = 공격 간격, 스킬 = `SkillData.castTime`(새 필드), 사망 = 사망 클립 길이(흐름 상수로 옮기는 것은 4단계).
3. **애니메이션은 비율만 정한다.** 정하는 것은 타격이 행동의 몇 % 지점인지와, 재생 속도 계산에 쓸 클립 길이다. 아트를 바꿔도 밸런스가 바뀌지 않는다.
4. **해제 개념을 없앤다.** 표식은 `AE_OnHit` 하나다. 옛 `AE_OnAttackEnd`/`AE_OnDeathEnd`는 클립 7개에서 지웠다. `AE_`로 시작하는 다른 이벤트가 있으면 굽기가 거부한다(오타나 옛 표식을 조용히 무시하지 않게).

**검토: 왜 이 방안인가**

| 대안 | 판단 |
|---|---|
| 스킬 길이를 시전자의 시간표(애니메이션 쪽)에 덮어쓰기 값으로 둔다 | 스킬의 밸런스 값이 아트 에셋에 흩어져서 데이터 표 하나로 조정할 수 없다. 기각 |
| 스킬 길이 = 클립 길이를 유지한다 | 지금 불일치의 원인이 그대로 남고, 아트를 바꾸면 밸런스가 바뀐다. 기각 |
| 해제를 남기고, 스킬만 해제 시점부터 끼어들게 한다 | "해제 뒤~완료" 구간은 스킬에게만 주는 특례다. 행동 종류마다 끊는 규칙이 달라지고, 그 구간의 길이도 아트가 정한다. 기각 |
| **시전 시간은 `SkillData`, 비율은 애니메이션, 취소 없음** | **채택.** 길이를 바꾸는 손잡이는 데이터 하나씩(공격 간격, castTime)이고, 순서 규칙도 하나(완료 뒤 결정)다 |

- 타이밍(비율)은 여전히 시전자의 애니메이션에 속한다. 같은 스킬 1번이 플레이어(Dash-Attack, 타격 40%)와 BossSlime(점프, 68%)에서 다른 지점에 맞고, 길이(1.0초)는 같다.
- 결정 입력 사건(`NextDecisionInputChange`)은 남긴다. 행동 중에는 결정하지 않으므로, 이 사건은 행동이 없을 때(대상이 없을 때, 기본 공격을 할 수 없는 시전자)에만 낸다. "결정 입력이 바뀌는 모든 순간에 결정한다"는 원칙은 그대로다.

**바뀐 것**
- `ActionTimeline`/`ActionTimelineBaking`: 해제 비율을 지웠다. 구운 값은 클립 길이와 타격 비율이고, 타격은 (0, 클립 길이] 범위다.
- `ActionRunner`: 표식은 타격과 완료뿐이다(`OnActionReleased` 삭제).
- `CombatActions`:
  - 행동이 없을 때만 결정한다(`IsFree`). 같은 뜻이던 `IsBusy`는 지웠다.
  - 스킬 길이는 `castTime`이다. 0 이하면 그 스킬은 쓰지 않고, 에러를 한 번 남긴 뒤 기본 공격을 한다.
- `PlayerDieState`: 사망 행동이 완료될 때 재시작을 알린다.
- `SkillData.castTime`: 지금 클립 길이와 같은 값을 넣어, 플레이어의 체감은 바꾸지 않았다.
  - 1 강타, 2 지진, 4 혼신의일격, 5 때리기 = 1.0초(Dash-Attack)
  - 3 힐링 = 0.6초(Croush)
  - 6 저주 = 0.9초(BossUndead Cast)
- 에디터·빌드 검사(`ActionTimelineTools.ValidateCombatData`)에 스킬 시전 시간 검사를 더했다.
- 테스트:
  - `CombatSchedulerTests`: 취소 없음 불변식(극단값 4조합에서 모든 행동이 타격을 다 내고, 다음 행동이 정확히 앞 행동의 끝에서 시작), 스킬 길이 = castTime, 잘못된 castTime의 대체 동작
  - `ActionRunnerTests`: null 수신자 반복 회귀 테스트
  - `ActionTimelineBakeTests`: 옛 표식 거부

| 할당 | 상태 전이마다 `new`, 범위 판정마다 `new List`, 스킬 효과마다 `Vector3[]` | R6 |
| 위치 | 로직이 `transform.position`을 읽고 쓴다. 그래서 단계 앞에서 보간 위치를 되돌리는 국면(①)이 필요하다 | 순수 C# 테스트를 할 수 없다 |
| 연출 | 데미지 숫자 색을 `target is PlayerController`로 정한다 | 타입으로 팀을 판단한다 |

### 8-2. 범위

| 넣는 것 | 빼는 것(다음 단계) |
|---|---|
| `Combatant`(순수 C#) 하나로 플레이어·일반 몬스터·보스 | 이동 속도·스크롤·월드 좌표(3단계). 지금의 이동 방식(스크롤 중 몬스터 이동, 보스 접근, CCD)은 그대로 옮긴다 |
| 상태 객체 8종 → 전투원의 단계 값(이동 / 교전 / 사망) 하나 | 인카운터·보스·스테이지 흐름, `PlayerDied`·`BossKilled` 같은 흐름 이벤트(4단계) |
| 거리 규칙 하나(표면 거리), 대상 규칙 대칭 | 로직에서 연출 호출 분리(5단계). 호출하는 곳만 호스트 한 곳으로 모은다 |
| 판정 몸(중심, 반너비)을 필수 데이터로 | 로직용 난수(8-9 D13) |

| 데이터만으로 일반 몬스터 공격 켜기, 데이터 검사 확장 | |

### 8-3. 구조

```
CombatSimulation (MonoBehaviour, 드라이버)
  └─ CombatWorld (순수 C#)
       ├─ SimClock, CombatScheduler (1단계 그대로)
       ├─ 전투원 목록 (등록 순서 = 동시 사건 순서. 플레이어가 먼저, 몬스터는 스폰 순)
       └─ 질의: 대상 찾기, 범위 안의 상대 (버퍼 재사용)

Combatant (순수 C#, 전투원 하나)          ICombatantHost (호스트가 구현: 연출만)
  ├─ 팀, 등록 순번                         ├─ 행동 시작(재생), 대기/달리기
  ├─ 몸: X(시뮬레이션 위치), 반너비          ├─ 피해·회복 숫자, 맞는 이펙트, 스킬 이펙트 위치
  ├─ 체력: Hp, MaxHp (GameNumber)           └─ 사망, 부활
  ├─ 능력: 공격력, 공격 간격, 사거리, 이동 정책, 스킬(SkillLoadout), 행동 시간표
  ├─ CombatActions (1단계 그대로. Combatant가 ICombatActor를 구현)
  └─ 단계: 이동 / 교전 / 사망

호스트 (MonoBehaviour, 그리기와 Unity 연결)
  ├─ PlayerController : 진행도(PlayerStats) → 능력, UI 입구(스킬 탭, 쿨다운 표시)
  └─ Monster          : 데이터(MonsterData × 스테이지 배율) → 능력, 보상, 풀. 보스도 이 클래스(역할만 다름)
     공통 기반 CombatantHost: 뷰, HP바, 판정 몸 설정, 시간표, X → transform(보간)
```

- **`Combatant`는 `UnityEngine` 오브젝트를 들지 않는다.** 위치는 `float X`이고, 시간표는 조회 인터페이스(`ActionTimelineSet`이 구현)로 받는다. 그래서 전투 규칙 전체를 씬 없이 EditMode 테스트로 돌릴 수 있다(R7의 일부. 5단계는 남은 의존 제거).
- **`BossMonster`를 없앤다.** 보스와 일반 몬스터의 차이는 데이터다: 스킬 있음, 이동 정책 "접근", 공격 간격 > 0. 보스 처치 알림은 보스 클래스가 아니라 스폰할 때 정한 역할(`보스`)로 낸다. 보스 프리팹 2개의 컴포넌트를 `Monster`로 바꾼다(에디터 스크립트, 필드 값 유지).
- **`PlayerController`와 `Monster`라는 이름은 남긴다.** UI, 스포너, 데이터베이스가 이 이름으로 연결돼 있고, 역할(호스트)이 이름과 맞는다. 공통 부분만 기반 클래스 `CombatantHost`로 올린다(같은 이름의 직렬화 필드라 프리팹 값이 그대로 이어진다).
- **위치의 주인은 `Combatant.X`다.** 로직은 `transform`을 읽지 않는다. 호스트는 화면 프레임마다 직전 두 단계의 X 사이를 보간해 `transform`에 쓴다. 그래서 단계 앞의 "보간 위치 되돌리기"(①)가 없어진다. y(바닥 높이)는 지금처럼 호스트가 정한다.

### 8-4. 규칙

**거리 하나.** 표면 거리 `gap(a, b) = |a.X − b.X| − a.반너비 − b.반너비`(겹치면 음수). 모든 판정이 이것을 쓴다.

| 판정 | 규칙 |
|---|---|
| 교전, 단일 대상 | `gap ≤ 사거리` |
| 범위 스킬 | `gap ≤ 반경` (지금은 중심 거리. 반경이 사실상 두 반너비만큼 늘어난다. 밸런스는 데이터로 조정) |
| 대상 고르기 | 반대 팀, 살아 있음, `gap`이 가장 작음. 앞뒤 구분 없음. 같으면 등록 순번이 빠른 쪽 |
| 대상 유지 | 지금 대상이 살아 있고 사거리 안이면 바꾸지 않는다(떨림 방지). 타격 순간 재확인(D3)도 같은 함수 |

**판정 몸.** 몸의 중심 = 피벗 + 오프셋 x, 반너비 > 0. 둘 다 프리팹의 필수 값이다(스프라이트 바운드 자동 계산을 지운다). 판정과 이펙트 위치가 같은 몸을 쓴다(D9).

**단계(상태 객체 대신 값 하나).** 고정 단계의 ③ 국면에서, 등록 순서대로 전투원마다 한 번:

| 지금 단계 | 조건 | 다음 |
|---|---|---|
| 이동 | 사거리 안에 대상이 있다 | 교전(`Engage`) |
| 이동 | 없다 | 이동 정책대로 움직인다 |
| 교전 | 행동이 없고(취소 없음) 대상이 없다 | 이동(`Disengage`) |
| 사망 | 사망 행동(시간표)이 끝났다 | 호스트에 알림(플레이어는 재시작 요청, 4단계에서 흐름으로). 사망 시간표는 기다릴 일이 있는 전투원(지금은 플레이어)만 갖고, 없으면 사망 즉시 끝난다 |

- **이동 정책**(지금 동작을 그대로 옮긴다): 플레이어 = 전진(이동 단계면 스크롤), 일반 몬스터 = 제자리(스크롤 중이면 화면과 함께 다가옴), 보스 = 접근(항상 다가옴). 모두 CCD(상대 몸을 통과하지 않음)를 쓴다. 몬스터의 정책은 몬스터 표의 새 열 `movePolicy`(Hold / Approach)다. 그래서 "다가오는 일반 몬스터"도 데이터만으로 만들 수 있다.
- **스크롤의 주인은 "아군이 이동 단계인가"다.** 지금의 `PlayerRunState` `Enter`/`Exit` 대신, ③에서 플레이어를 먼저 처리하고 그 결과를 같은 단계의 몬스터 이동이 읽는다(지금과 같은 순서). `OnScrollChanged` 구독은 없어진다.
- **기본 공격 능력은 데이터다.** 공격 간격 > 0이면 기본 공격이 있다. 없으면 교전하지 않는다(지금의 일반 슬라임: 간격 0). 엑셀에서 슬라임의 간격·공격력·사거리를 넣으면 코드 수정 없이 슬라임이 공격한다. 이를 위해 슬라임 프리팹에 시간표(BossSlime과 같은 점프 클립)와 애니메이터 `Attack` 상태를 미리 둔다.

### 8-5. 수치: HP·데미지 `GameNumber`

- `Combatant`의 HP, 최대 HP, 공격력, 받는 피해·회복량이 `GameNumber`다. 데미지는 `GameNumber.Round(공격력 × 배율)`(정수 값 유지).
- 몬스터: `MonsterData`의 `int` × 스테이지 배율을 `Math.Pow`(double)로 계산해 `GameNumber`로. 표(`MonsterData`)와 저장 DTO는 지금처럼 `int`/`double`(구조체를 직렬화하지 않는다).
- 플레이어: `PlayerStats.MaxHp`/`AttackDamage`도 `GameNumber`로 바꾼다(계산은 double). 업그레이드 표시 API(`IUpgradeStat`의 float)는 UI 이관 때 정리한다(D14).
- 이벤트와 UI: 피해·회복 이벤트, HP 변경 이벤트가 `GameNumber`를 싣는다. HUD, 체력바, 데미지 숫자는 `NumberFormatUtility.Format(GameNumber)`(이미 있음)로 그린다.
- 극단값: HP 1e30, 데미지 1e30에서도 음수·NaN이 없고, HP는 0 아래로 내려가지 않는다(테스트).

### 8-6. 할당 0 (R6)

| 지금 할당 | 바꾼 뒤 |
|---|---|
| 상태 전이마다 `new` 상태 객체 | 단계 값(enum) |
| 범위 판정 `new List` | `CombatWorld`가 가진 버퍼를 재사용 |
| 스킬 효과가 `Vector3[]` 반환 | 맞은 전투원을 버퍼에 담고, 연출은 그 전투원의 호스트에서 위치를 얻는다 |
| 스폰마다 상태 객체·런타임 객체 | 호스트(풀)마다 `Combatant`를 하나 만들어 두고 스폰 때 값만 다시 채운다 |

- 측정: 플레이어 1 + 몬스터 5, 범위 스킬과 사망이 섞인 전투를 `CombatWorld`로 수천 단계 돌리면서 할당이 0인지 EditMode 테스트로 확인한다(Unity Test Framework의 `Is.Not.AllocatingGCMemory()`). 연출(호스트)은 테스트에서 가짜로 둔다. 진짜 연출(이펙트 풀, 소리)의 할당은 5단계에서 다룬다.

### 8-7. 데이터와 검사

- **판정 몸 필수:** 모든 전투원 프리팹은 반너비 > 0. 에디터를 열 때와 빌드 전에 검사한다(지금 `ActionTimelineTools.ValidateCombatData`에 더한다).
- **능력과 연출의 짝 검사:**
  - 몬스터 데이터의 공격 간격 > 0이면 그 프리팹의 시간표에 `Attack`이 있어야 한다.
  - `skillId`가 있으면 그 스킬이 있고, 그 스킬의 행동 키가 몬스터 시간표에 있어야 한다.
  - 플레이어가 배울 수 있는 모든 스킬의 행동 키가 플레이어 시간표에 있어야 한다.
  - 지금은 이런 어긋남이 런타임 에러(시간표 없음)로만 드러난다. 데이터를 고친 사람이 플레이 전에 알게 한다.
- **보스 프리팹의 사거리·간격 필드는 지운다**(엑셀 값으로 덮어써서 쓰이지 않는 값).
- **플레이어 사거리·이동 속도의 출처(D12):** 엑셀에 캐릭터 시트(`CharacterData`: id, 이름, 사거리, 이동 속도)를 더한다. 몬스터처럼 이름으로 프리팹을 연결하고, 플레이어는 이 표의 캐릭터(지금은 전사 한 줄)로 스폰한다. 직업·동료가 생기면 이 표가 그대로 늘어난다. 이동 속도는 값의 출처만 옮기고 쓰는 방식은 3단계에서 바꾼다.
- **튜닝 덮어쓰기(D15):** 엑셀을 고치지 않고 값을 바꿔 보는 에디터 전용 층. "표 / id / 열 / 값"으로 적고, 변환기와 같은 형식 검사를 한다. 게임이 데이터를 읽을 때 사본(`Instantiate`한 데이터베이스)에만 덮어써서 엑셀도 `.asset`도 바뀌지 않는다. 내 PC 전용 파일(`UserSettings/`)에 저장해 저장소에 올라가지 않는다. 켜져 있으면 플레이 시작 때 경고하고, 빌드에는 이 코드가 없다(빌드 전에 "남은 덮어쓰기가 있다"고 알린다). 플레이 중에 바꾸면 그 자리에서 다시 적용된다: 데이터 객체를 바꾸지 않고 값만 고치므로 플레이어는 바로, 몬스터는 다음 스폰부터 반영된다. 확정한 값은 목록을 보고 엑셀에 옮긴다.

### 8-10. 순서와 검증

1단계와 마찬가지로 단계 안에서도 게임이 도는 상태를 유지하며 나눠서 한다.

1. **`Combatant`/`CombatWorld` + 판정 통일 + 단계 값**(D8, D9, D10, D11): 동작을 옮긴다. 기존 측정 중 케이던스, 결정성 4종, 정지 시드 3개는 범위 스킬을 쓰지 않는 세이브(스킬 1 강타, 단일 대상)라서 처치·타격 시각이 7-13 결과와 **같아야 한다**. 보스 측정은 D9로 BossUndead가 서는 위치가 바뀌어 달라질 수 있다. 범위 스킬은 새 측정을 더해 반경이 표면 기준인지 본다.
2. **`GameNumber`**(D5, D14): 극단값 테스트(HP·데미지 1e30, 0, 회복 넘침).
3. **할당 0**: 측정 테스트.
4. **데이터**(D12, 슬라임 공격 준비, 검사 확장): 엑셀에서 슬라임 공격을 켜면 슬라임이 공격하는지 에디터에서 확인하고 되돌린다. 잘못 짝지은 데이터(시간표 없는 공격, 없는 스킬)를 검사가 잡는지 확인한다.
5. **S24 확인**: 보스 2종(특히 D9로 BossUndead 위치), 범위 스킬.

새 테스트(EditMode, 순수 C#):
- 대상 규칙: 뒤쪽 대상, 같은 거리의 순번, 유지형, 겹침(음수 거리), 반너비 0과 아주 큰 값
- 범위: 표면 기준 경계(정확히 반경, 바로 바깥)
- 단계 전이: 공격 능력이 없는 전투원은 교전하지 않음, 데이터로 켜면 교전, 사망 시간표 완료 알림
- 수치: 극단값
- 할당: 0

**이 단계가 끝나면:** 전투원 클래스가 하나이고, 판정 규칙이 하나이며, 일반 몬스터의 공격과 수치 한계가 데이터 문제로 바뀐다. 전투 규칙 전체를 씬 없이 테스트할 수 있다.

### 8-11. 결과 (2026-11-24)

**구현:** 8-8의 표대로다.
- 새로 만든 것: `Combatant`, `CombatWorld`, `ICombatantHost`, `CombatantHost`, `CharacterData`(+ Syncer, DB, 엑셀 시트), `DataTuning` + 튜닝 덮어쓰기 창, `IDataTable`, `CombatDataValidator`
- 지운 것: `BossMonster`, 상태 8종 + `StateMachine`/`IState`, `CombatRangeUtility`, `ISkillCaster`, `IDamageable`
- `PlayerController`와 `Monster`는 호스트로 줄었다.

**설계와 달라진 점**
- **보스 프리팹 교체:** 에디터 스크립트 대신 프리팹의 스크립트 참조(GUID)를 `BossMonster`에서 `Monster`로 바꿨다. 필드 이름이 같아 값(시간표, 판정 몸)이 그대로 이어지는 것을 확인한 뒤 다시 저장했다(쓰지 않는 옛 필드는 지워짐).
- **이동 단계의 순서:** 움직인 뒤에 대상을 본다(예전 보스 접근 상태와 같은 순서). 움직여서 사거리에 들어오면 같은 단계에 교전한다.
- **단일 대상 스킬이 헛치면 이펙트를 그리지 않는다.** 예전에는 시전자 위치에 그렸다. 지금은 맞은 전투원 목록만 연출에 넘긴다.
- **할당 측정이 1단계부터 있던 할당을 찾았다.** `CombatActions`가 스킬을 시작할 때마다, 검사가 통과해도 에러 메시지 문자열을 미리 만들고 있었다. 이제 메시지는 실패할 때만 만든다.
- **테스트와 플레이 측정을 배치 모드로 했다.** 켜 둔 에디터에서 테스트를 돌리는 것이 실행 권한 검사에 막혔다. CLAUDE.md 규칙(반복·시간 코드를 크게 바꾸면 배치 모드 먼저)대로 사용자가 에디터를 닫고 진행했다. 플레이 측정은 임시 러너를 `-executeMethod`로 시작해 끝나면 에디터를 종료하게 했다.

**남은 것**
- 이동·스크롤·속도는 3단계다. 몬스터는 아직 "스크롤 속도 = 플레이어 이동 속도"로 움직이고, 캐릭터 표의 `moveSpeed`는 그 값의 출처만 옮긴 것이다.

- 업그레이드 표시 API(`IUpgradeStat`)는 float다(UI 이관 때).
- 로직용 난수는 쓰는 기능이 생길 때 만든다(D13).
